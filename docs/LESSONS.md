# Lessons

Cross-cutting lessons from building mettle — the ones without a more specific home. When a lesson belongs in a rubric (STYLE / PORTING_RULES), a decision ([ADR](adr/)), or a reference gotcha ([reference/](reference/)), put it **there** and just cross-link from here. Filed as part of the [session wrap routine](SESSION_WRAP.md).

## Process / working model
- **Delegate volume, verify the consequential claims yourself.** Background sub-agents carried real load well (`sonnet` for verify-heavy research, `opus` for taste-heavy docs). But the tech lead re-ran the single most verdict-affecting agent finding by hand (the integer-overflow default) instead of trusting the summary — and it mattered. Independently re-verify anything that changes a verdict. → [CLAUDE.md](../CLAUDE.md) Delegation policy.
- **Cold-test the handoff.** A fresh-context, read-only agent given only the repo + "proceed" is a cheap, honest test of whether the docs actually carry the next session. It caught an uncommitted-instruction gap we'd otherwise have shipped. → [SESSION_WRAP.md](SESSION_WRAP.md) §5.
- **Two entry points, one destination.** A session started in `~/repos/mettle` auto-loads the repo `CLAUDE.md`; one started in the website dir auto-loads the cross-session memory instead. Both must funnel to `docs/STATE.md`. Keep both current.
- **Never let project-owned code live in a git-ignored directory.** mt-006's delegated shim landed in `oracle/` (ignored wholesale for legal hygiene) — it built and tested fine locally while being silently uncommittable; a fresh clone would have lost it. Review caught it; the fix is structural: first-party code goes inside a crate (`crates/als-conform/shim/`), ignored dirs hold only re-downloadable third-party artifacts. Check `git status` untracked output against "what did we write ourselves" at review time.
- **Byte-identical reproduction audits your documentation for free.** mt-009's acceptance bar ("the fetch script must rebuild `corpus/` byte-for-byte") surfaced that the provenance manifest under-documented the upstream pipeline (a 4th patch the prose called 3). Prose records drift; a reproducibility check against reality is the cheapest honest reviewer. Prefer "regenerate and diff" acceptance criteria over "matches the description" wherever possible.
- **Spec from the implementation's sources, then jar-probe the surprises — never from the published grammar or memory.** Rung-1's syntax contract came from reading `Alloy.lex`/`Alloy.cup`/`CompFilter` at the jar's build commit; that surfaced behavior no documentation states (five token-stream rewrites, `::` ≡ `.`, `Version.experimental=true` gating live syntax, hex-digit *pairs*). Where the generated-lexer semantics (longest-match + rule-order tie-breaks) made the raw patterns misleading, one round of jar probes settled it (`1_000` is illegal!). The spec doc records *behavior*, with every surprising claim jar-verified and dated. → [reference/alloy6-grammar.md](reference/alloy6-grammar.md).
- **A delegate's "benign divergence" list is a review queue, not a footnote.** mt-011's report flagged four divergences as benign; adjudicating each against the reference showed two were not (`;`-grouping changed formula semantics under `after`; prefix over-acceptance broke error parity). The delegate's *report* was the review input that made this cheap — require divergence lists in every delegation report, then verify each one independently before merge.
- **A grammar-narrowing change costs double: parser AND printer must move in lockstep.** mt-014's binder-composition fix (restricting what parses) immediately broke the parse→print→reparse round-trip — the printer's "when do parens matter" logic embodied the old, looser grammar and started under-parenthesizing. The structural cure was the mt-012 pattern extended: put the rule itself (`child_binder_budget`) in the shared `prec` module both sides consume, so drift is impossible by construction. Budget any future grammar-restriction bead as a parser+printer change, never parser-only, and let the round-trip corpus test be the tripwire (it caught this one).
- **Big corpora + real-world junk find what specs and unit tests don't.** The alloy4fun differential pass (mt-013) and the mutation fuzzer (mt-014) each found real bugs the 167-file curated corpus never touched: student typos exercised grammar corners (bare `disj`, trailing `^`), byte-level mutants found the printer under-parenthesization, and deep-nesting stressors proved the parser could SIGABRT a debug test worker at ~212 paren levels (fixed with `MAX_EXPR_DEPTH`, a *measured* limit — measure stack headroom on the smallest relevant stack, don't guess). Cheap, deterministic, seeded — keep both in CI forever.
- **Concurrent agents in one working tree work if partitioned by path.** Two background delegations + tech-lead coding ran simultaneously with zero conflicts by (a) giving each a disjoint file-path scope up front, (b) banning workspace-wide `cargo fmt`/`clippy` in agent specs (package-targeted `-p` only), and (c) the tech lead committing per-scope with pathspec `git add`. Cheaper than worktrees for disjoint work; use worktrees only when paths must overlap.
- **Measure a tightening before shipping it — the reverted-tightening loop is a feature, not waste.** ADR-0009 deferred the resolver's ambiguity rejects pending data; when the mt-020 gauge crossed the trigger, the tightening was implemented, measured (28,402 false rejects vs ~1,478 gains — coarse types, not choice logic, were the blocker), and *reverted* with the numbers recorded. One day of implement-measure-revert bought certainty a design review never could, and turned "tighten now?" into a filed, evidence-priced bead (mt-022). Wire "the gauge decides" into any ADR that defers correctness work.
- **Close a rule's residuals with probes BEFORE asking the owner to ratify it — the matrix is cheaper than the mistake.** LEDGER-004 was first put to the owner with a "re-derive at implementation" caveat attached; the owner pushed back ("if stating the rule wrong is a risk, do research to reaffirm it"), and the resulting 19-probe matrix found a real hole — util/ordering's exact-constant pinning silently switches OFF when the ordered sig has subsigs, so the original unconditional rule would have shipped wrong instance counts on every ordered-sig-with-subsigs model. Process now codified in the Ledger: entries reach the owner only at `verified` = zero open residuals. Corollary: a residual flagged in any spec doc is a probe backlog, not a footnote.
- **Restate the clean-room prohibition in EVERY delegation that could plausibly touch the stdlib — and provenance-check any stdlib diff at review.** mt-025's spec was resolver-scoped, so it didn't repeat the ADR-0006 rules; mid-bead the agent legitimately cloned the reference's *Java* sources, then drifted one directory over and read upstream `util/ordering.als` body text to fix a stdlib bug it had exposed — a real contamination, caught only because the tech lead challenged the report's phrasing ("the jar's own ordering uses…") before merging. Remedies that worked: the agent's honest, file-exact accounting; reverting the tainted line; re-deriving it via a fresh agent given only the interface + the resolver's error. Rules: (1) every delegation whose scope *could* brush `crates/als-types/stdlib/` carries the prohibition verbatim, including the scratchpad-clone path; (2) any diff to a clean-room file triggers a provenance question at review, always; (3) a report sentence that implies upstream knowledge ("matches upstream", "same as the jar's") is a tripwire, not color.
- **Interface listings must be per-member precise before a clean-room author starts.** mt-015's first pass had to guess where the §7 interface summary was condensed — and four guesses were wrong (param shapes, arities, a field name). The fix that worked: the spec-side agent (the only one allowed to see upstream) produced a structured per-member appendix (names, param order, types, multiplicities, private markers), and the clean-room author revised against it without ever seeing source. Split the roles that way from the start; an honest "I guessed here" list in the author's report is what makes the loop cheap.

- **Never "time out" work by abandoning its thread — and know that a swallowed panic looks exactly like a timeout.** The mt-039 incident: `solve_corpus`'s worker-thread-plus-`recv_timeout` harness leaked every over-budget solver (they kept allocating forever → machine OOM, twice), and — worse — a *panicking* worker dropped its channel, which the caller cannot distinguish from a timeout, so real encoder bugs were silently counted as `over_budget` for two beads while the suite claimed "0 panics". Cures, both structural: (1) budgets live *inside* the computation as deterministic effort counts (solver conflict budget, encoder effort meter — a *clause* cap alone is blind to constant-folded grounding work, meter the gate *requests*), so stopping actually frees memory and the bucket counts are machine-independent; (2) failures are caught per-item (`catch_unwind`), inventoried by name, and still fail the suite — one sweep enumerates every latent bug instead of hiding them or dying at the first. Generalization: any harness that converts a failure signal into a benign-looking bucket is manufacturing false confidence; make failure modes distinguishable by construction.
- **A fixed dropped-flag bug indicts its whole flag family — sweep the siblings before closing the bead.** mt-038's headline fix was `Decl.is_disj` never reaching `ResolvedField` (a silent under-constraint → the one wrong corpus verdict). Only at the wrap review did a grep for the *adjacent* flag reveal `is_bound_disj` (`f: disj e`) had the exact same lifecycle: parsed, printed, and read by nothing downstream — a second silent under-constraint one field over, invisible because the corpus never uses it. The cheap discipline: when any carried-but-unread field is found, grep the struct for every sibling with the same producer and no consumer, and either implement or *typed-defer* each one the same day. Zero-corpus-incidence is an argument for a defer, never for a silent drop.
- **When a fix unlocks a new code path population, expect the *pre-existing* bugs it exposes to be misattributed to the fix.** mt-035 unlocked ~270 ordering commands; the 8 wrong verdicts that appeared all pattern-matched to "the new ordering code is wrong" but every one traced to older latent bugs (HO-quantifier per-tuple mis-lowering, quant-var arity) that had simply never been reached (or whose panics were swallowed). Triage discipline: minimal repro + conjunct-drop bisection *before* touching the new surface.
- **An agreement can be two bugs cancelling — a differential gauge only certifies verdicts, not the reasons for them.** mt-037's sharpest find: hotel1.als "agreed SAT" with the jar only because a dropped `in`-arrow multiplicity (bug A) admitted a bogus counterexample that masked the stdlib's swapped `min`/`max` (bug B); fixing A flipped the file to a *wrong* UNSAT, which looked exactly like a regression in A. The bisection that untangled it: scope-shrink the disagreement (1 Room made the suspect fact vacuous — instantly acquitting it), then force the reference's witness story step-by-step and test each step's conjuncts. Corollaries: (1) a fix that "creates" a disagreement has usually *exposed* one — triage before reverting; (2) semantic pinning tests for clean-room code are non-negotiable — min/max survived two beads because resolve-level gauges and bounds probes never once evaluated them (the swap was invisible to everything but a solve).
- **A subagent's detached background process dies with the subagent's task — long measurements belong to the coordinator, time-bounded.** mt-049 stalled twice on the same shape: the delegate launched a long gauge run "in the background", ended its turn to wait, and the harness reaped the process group the moment its task closed (`/usr/bin/time` killed before writing its summary; zero output). The delegate's own report then claimed it was "awaiting the run's completion notification" — a wait that could never end, and it read exactly like healthy progress until the tech lead checked `ps`. Rules: (1) any measurement longer than a delegate's foreground window runs as the *coordinator's* tracked background job, never the delegate's; (2) a delegate saying "waiting for my background run" is a tripwire — verify the process exists before believing it; (3) every open-ended budget/perf probe gets a hard `timeout` — an unbounded probe at generous budgets re-created the known mt-037 grind mode (8.5 CPU-hours, zero output) where a 40-min `timeout` turned "is 2× budget tractable?" into a cheap yes/no experiment. The mt-039 lesson generalizes past threads: *any* abandoned computation is a leak; make some supervisor own every long-running child. **mt-045/046 addendum: prompt instructions do not fix this.** Three consecutive delegates (two opus, one sonnet) ended their turn "waiting for the notification" even when the spec said, verbatim, "run in the FOREGROUND — do not use background execution; your final message must contain the numbers". The delegate's wait-instinct on long commands is stronger than the instruction. Working structure: treat the delegate's deliverable as *code + fast targeted gates only*, and plan for the coordinator to run every slow gate (full gauntlet, gauge sweeps) as its own tracked background jobs afterward — i.e., stop paying the spec words that ask a delegate to babysit long runs, and stop treating a delegate's truncated final report as a failure when the tree state is complete; verify the tree directly.
- **A probe's SPELLING is part of its evidence — validate the probe language before trusting any matrix built in it.** mt-044 paid for this twice in one day. (1) mt-043's `div[MIN,−1]=1` was wrong because `(0-1)` is not −1 — the raw hyphen is relational set-difference (`(0-1)` = the atom `0`); only `(0-8)` is special (the MINUS peephole for the unwritable most-negative literal). The mispinned row was silently `div[MIN,0]`. (2) Far worse: the "clean" replacement spelling `negate[k]` is itself poison at `k=8` in forbid mode — `negate[8]` computes `minus[0,8]`, which genuinely overflows, so it carries a permanent overflow flag that silently EMPTIES any conjunction-shaped quantifier domain it bounds (`x>=negate[8] and x<=…` → no atoms → vacuous ∀). An entire "second guard defect" (nesting-position-dependent, 8 decisive probes, a 2×2 deconfounding matrix) was manufactured by this artifact and had to be retracted a round later. Disciplines that would have caught each a round earlier: reflexivity controls in the probe language itself (`run { negate[8]=negate[8] }` forbid-UNSAT screams "the spelling is not inert"); and when a probe matrix implies a mechanism the source code cannot explain (the round-2 agent honestly wrote "self-contradictory derivations"), treat that as evidence AGAINST the probes, not as a mystery to document. An honestly-flagged unexplained mechanism is a tripwire for a confounded harness.
- **Review the coverage of a delegated probe matrix against the DEPLOYED shapes, not just the asked-for shapes.** The round-2 polarity matrix answered every requested corner yet omitted the two cells real models actually use — mixed nesting over bare `Int` (no comprehension anywhere) and sig-bound quantifiers as overflow drivers. The sig-domain gap concealed a live wrong-verdict risk on the single most common corpus shape (`all p: Sig | #…` never gets universal-rescue in the jar), which the ideal published rule — and the implementation being built from it — predicted backwards. Tech-lead review of a probe deliverable must ask "which cell does the corpus live in?" and demand that cell explicitly; an agent answers the question it was asked.
- **When unpinned semantics are discovered mid-implementation, the sequence is probe-first, defer-if-unpinnable — never implement the guess.** mt-044's shift barrel was built (and "exhaustively tested") against an assumed saturation semantics; five minutes of jar probes showed the amount is masked to `⌈log2 w⌉` bits (`1<<4` at bw4 is a no-op, not 0) and that `<<` has a genuinely spurious junk-bit overflow defect mettle must replicate. The agent's exhaustive table tests validated the circuit against the agent's own wrong closed-form — self-referential test oracles reproduce assumptions, they don't check them. Any cell not backed by a jar probe or pinned source is either probed before coding or typed-deferred.
- **A budget binds only if it is denominated in the thing that actually costs time — and you prove that on the pathological case BEFORE the full run.** mt-047's counting net ground for 3 hours twice, through two wrong denominations: a *conflict* budget never ticked on propagation-bound enumeration (thousands of easy instances, ~zero conflicts each), and a *decision* budget missed that each decision's cost is unbounded (huge watch lists + accumulated blocking clauses). The denomination that works is the one proportional to wall time: **propagation clause-visits** (+ conflicts + decisions), a deterministic counter in the solver's hot loop. Both wrong versions shipped because the fix was validated only on fast targeted tests, never on the known-grinding file — each full run then burned hours before failing. Standing rules (owner-directed, in memory as owner-runtime-deadlines): every long invocation carries a hard `timeout`; the gauge emits a stderr **liveness heartbeat** (per-command start lines, `took X.Xs`, slowest-10 table) so a stuck run is diagnosed from its last line, not archaeology; stdout stays the deterministic report (capture with `> report 2> progress`, never `2>&1`); and any budget/deadline change is validated wall-clock-measured on the pathological corpus members (correctChord, ptcris, the addressBook counting commands) before any full sweep. Corollary: when a fix newly unlocks work (mt-047 made 2× the commands countable), re-derive the outer deadline from the new workload instead of reusing the old one — two of today's "failures" were just yesterday's deadline on tomorrow's run.
- **A defer bucket's size is not its structure — classify per-command before treating a bucket as a "family", because one shared fact can fan a single bug into N rows.** mt-050's exit prep assumed the gauge's `lowering 36`-row majority was the Rung-6 temporal-adjacent family its file (an LTL-style elevator model) suggested; a per-command classification pass with minimal repros showed all 36 were ONE Rung-3 bug (a formula-valued `let` forced down the relation-lowering path) reached through a single shared fact — fixable in an afternoon, and its fix moved agree 301 → 343 because the file's commands then solved and matched 33 fresh jar expects. Bucket labels aggregate symptoms, not causes; before an exit gate (or any scoping decision) prices a bucket, spend the cheap pass that re-runs each member and bisects the distinct reasons. Corollary: when a bucket is dominated by one file, suspect one cause, not many.
- **An implementation that keys on a convenient PROXY of a pinned mechanism is a filed divergence waiting to happen — and when one surfaces, re-read the pinned contract before re-probing from scratch.** mt-041's whole mystery ("how does the jar detect the ordering module? module path? sig label? field names?") sat filed for six days while translation-ref §5 already stated the mechanism correctly: `TranslateAlloyToKodkod` fires on a `pred/totalOrder` whose args are plain relations — no module identity anywhere. mt-035's implementation had quietly substituted the proxy "module header == util/ordering + fields named First/Next" (true for every opened instance in the corpus, false for the module run as its own root), and nothing recorded that the shipped trigger was narrower than the pinned one. Two rules: (1) when an implementation narrows a pinned mechanism to a proxy that happens to cover current cases, that narrowing is a LIMITATIONS entry at merge time, not an implicit simplification; (2) a divergence bead's first triage step is to diff the implementation against the already-pinned contract — the mt-041 probe matrix (7 rows) confirmed what §5 said all along, and the only genuinely new fact was the root-module `exactly`-param path (`addModelName`).
- **A probe agent's RULE is a hypothesis about its own cells — test it against the cells it did NOT run, starting with the already-pinned regression suite.** mt-051's probe agent executed 27 cells flawlessly (every one reproduced) yet generalized them into a wrong rule ("no quantifier dependency ⇒ no guard") because its three supporting cells shared a hidden property (fully-constant translations). The refutation cost one grep: the mt-044 jar-pinned tests already held closed-operand cells (`plus[7,7]<0`, `#A=8`) that contradicted the proposed rule on a path the agent never probed. Review discipline: before accepting a delegated rule, (1) diff it against every existing pinned test row — a proposed rule that flips a shipped pinned verdict is wrong or the pin is, and either way you probe; (2) ask what property the supporting cells share besides the claimed one, and design the cell that splits them (here: closed-but-variable-circuit, which took three hypotheses down in one run). Related tripwire, again: the agent honestly flagged "source predicts the opposite of my probes" — that flag was, again, the confound speaking (as the LESSONS entry two above predicted), and chasing it mechanically (javap on the actual bytecode, then the env-less `Int.eq` discovery) is what turned a contradiction pile into one clean mechanism.
- **The probe-spelling ledger must be consulted at probe-WRITING time, not just probe-reading time.** Even after mt-044's `(0-1)`/`negate[8]` entry (directly above), the mt-051 tech-lead verification round itself spelled −2 as `(0-2)` and burned four cells on the identical artifact — the peephole is literally `0-(max+1)` only. The general form: any probe DSL has a small list of known-poison spellings; paste that list into every new probe file's header comment before writing cells (the mt-051 files now do). Silver lining: chasing the confound is what surfaced that mettle lacks the MINUS peephole entirely — a real divergence, filed as mt-052. A spelling artifact you bottom out fully often pays for itself.
- **Parse the artifact, don't eyeball it — the tech lead mis-read the same JSON format twice in one session, in opposite directions.** Sizing mt-059 from `baselines/*-count-sb0.json`, a hand-rolled loader reported "`mesh` has no count baseline at all" and "267 of 564 commands have no entry". Both wrong, and the same error: the file nests everything under an `entries` key, and a **file-level** marker (`"timeout"` for a whole file) answers for *every* index of that file. `mesh` has an entry; true misses are **zero**; 267 was the file-level-timeout population. The delegate caught both by reading `lookup`/`disposition` instead of the raw file, and the corrected numbers made the win *bigger* than specced. Rules: (1) when a number will end up in a bead, a commit message or a gate, derive it through **the same code the gauge uses**, never a throwaway script over the JSON; (2) a loader that silently `continue`s on a parse exception will report "0 hits" for a structure it never understood — make it fail loudly; (3) `0 results` from your own script is a claim about your script until proven otherwise. Cost this time was only embarrassment (the conclusion held); the same mis-read in a semantics bead would have shipped a wrong rule.
- **Every performance bottleneck this project has had was discarded work or scheduling — never slow code. Pick the instrument by the class of problem.** Three for three: mt-054 was a JVM spawned per file; mt-057 was one file as a serial critical path with nine of ten cores idle (**1.18× effective parallelism**, visible only in the CPU-vs-wall ratio); mt-059 is computing an answer before checking whether anything is asking for it (753s of an 882s wall enumerating a command with **no jar baseline to compare against**, which then exhausts its budget and produces nothing). **A CPU profiler would have reported "time in SAT solving" all three times** and sent us to optimize the solver — the one change the determinism contract makes most expensive. Diagnostic order that actually worked: (1) CPU÷wall against core count — a ratio far below the job count means scheduling, not code; (2) per-item accounting — if one item is most of the total, that item *is* the schedule; (3) **bucket the output and ask what gets thrown away** — work whose result lands in a skip/defer bucket is pure waste and no amount of optimizing it helps; only when all three are clean does a sampling profiler earn its place, aimed at **one deterministic command**, never a sweep.
- **Optimize against the pathology, or you will measure a win that isn't there.** mt-057's fast lane benchmarked at 3.7× on the alloytools subset and delivered **8%** on the real corpus — because the subset didn't contain `correctChord.als`, which was 556.5s of a 560s run. The tech lead caused this by telling the delegate not to run the full sweep (reasonable — it's 10 minutes) without naming the one file that had to be in whatever subset they chose. Rule: when delegating performance work, **name the known-pathological input as a required benchmark case**, and treat any speedup measured without it as unvalidated. Corollary: a delegate reporting a big number on a subset is not overclaiming — the spec is what failed.
- **A speedup that trades coverage should be re-measured after the speedups that don't — it may have become worthless.** mt-057's capacity-skipping was worth ~10 minutes when the sweep was file-serial; once command-level parallelism landed, the *same feature* was worth 6%, while still carrying its blind spots (a previously-capped command becoming newly solvable *and wrong*; panics on the largest models). It was deleted rather than kept "since it's already written". Sequence correctness-preserving optimizations first, then re-price every correctness-trading one against the new baseline — sunk implementation cost is not a reason to ship a hazard.
- **A coordinator's confident correlation is a hypothesis, not a lead — and steering delegates with it costs double.** At mt-055 the tech lead noticed that `rf_p`, used *directly* at the top of the acyclic union, appeared in exactly the two divergent commands and in none of the three matching ones, and handed that to both delegates as "the sharpest localizer". It was a **coincidence**; the real cause (a skolemization-blocking rule) had nothing to do with `rf_p`, and one whole measurement campaign was built around the dead axis before being stood down. A discriminator that separates the failing cases is evidence that *something* differs — it is not a mechanism, and it should be labelled as an untested hypothesis in the delegation spec, ranked below "here is the method for finding the mechanism". Corollary that saved this bead: the second delegate was given a *method* (pin an instance, bisect the formula with Kodkod's `Evaluator`) rather than only the hypothesis, and the method is what worked.
- **A fix for a class of bug leaves holes of its own class — review must ask "where else does this rule apply?", not just "is this diff right?"** mt-055 mirrored Kodkod's skolemization-blocking rule into `and`/`or`/`implies`/blocks, shipped green with 9 jar-pinned tests, and still left formula-valued `if/else` unblocked — the *same* rule, one node type away, jar-pinned wrong. It surfaced only because the adversarial pass was briefed to hunt for un-covered paths (n-ary forms, ITE, `let`, inlining, comprehensions) rather than to audit the diff. When a change encodes a *rule*, the review checklist is an enumeration of the IR node types that rule can reach; a passing test suite says nothing about the nodes nobody thought to test.
- **Prose baselines go stale silently — diff a fresh before/after on the same tree, never the numbers in a doc.** mt-055 nearly reported a regression from a bucket figure recorded in STATE.md (SB-0 `enum_budget 52`) that was wrong by 27; a same-tree re-measure showed the true pre-fix value was 79 and the change was a strict improvement. Cost of finding out: 28 minutes of re-derivation, on top of a 47-minute battery. Two rules: (1) any claim of the form "X moved from A to B" requires A measured on the current tree, not read from a doc; (2) headline numbers belong in a machine-diffable committed artifact with a config header and tree hash, which is what mt-057 item (3) exists to build. → [TASKS.md](TASKS.md) mt-057.
- **A delegate interrupted by infrastructure failure is a RESUME, never a respawn — and pace the retries.** During mt-063 a platform outage (API 500s plus the tool-gating classifier going unavailable) killed the probe agent three times mid-campaign. Everything survived: the agent's transcript (resumable with a message, warm context intact) and its on-disk artifacts (harness, fixtures, extracted bytecode). Respawning fresh would have discarded both and risked divergent duplicate work. What worked: (1) read the failed agent's transcript tail / workspace first to learn exactly where it stopped — the resume message can then say "X and Y exist, Z doesn't yet"; (2) after two immediate-retry failures, stop hammering — arm a background backoff timer (a few minutes) and retry on its notification; the third resume after backoff ran to completion; (3) tell the resumed agent how to handle recurring denials ("wait ~60s and retry that call") so it doesn't abort itself on the outage's tail. The general shape: infrastructure failures are checkpointable interruptions, not task failures — treat them like a killed build, not a wrong answer.
- **A prune's verify-before-delete rule protects against LOSS, not against STALENESS — review the kept text against the present, not just the deletions.** mt-060's delegate faithfully verified every deleted STATE.md block existed elsewhere before deleting (zero facts lost, exactly as briefed) — and just as faithfully preserved kept prose that was flatly false: the current-rung paragraph still ended "We are now at the Rung-3 exit / owner touchpoint" (three rungs stale), and the inventory still said "not yet published to a remote" (stale since mt-042a). A brief scoped to "don't lose anything" produces a delegate that treats stale sentences as facts to protect. Review discipline for any doc-pruning delegation: after auditing the deletions, read every *retained* paragraph asking "is this true today?" — grep for superseded-sounding phrases ("we are now at", "not yet", "next:") and check each against the current state. Better: put "flag any kept sentence that contradicts the header's current-state claims" in the brief itself.
- **A contract's shorthand sentence is itself a hypothesis — probe the load-bearing semantic cell before implementing it, every time.** Rung 6's implementation run refuted three *natural readings of our own pinned contract/ADR* before they shipped, each via a prediction-first probe the bead spec demanded: ADR-0015's "past operators walk the honest prefix" (P-D2 — the jar evaluates past against the true lasso history; the ADR was amended in place), the "eval normalizes the state then evaluates" reading of §(h) (P-068-1 — the jar evaluates at *logical time*, pasts accumulate across loop passes; only the GUI arrows pre-normalize), and the "read `exactly N..M` as the written range" fallback (L6 — the jar silently discards `M`). All three were wrong-verdict-or-wrong-behavior class, none was visible in any corpus gauge, and each cost one probe fixture to catch versus a shipped divergence to unwind. The discipline that worked, now standing: any bead implementing a semantic cell states its predicted jar behavior *in writing* first, and the spec names the highest-risk cell and requires it probed **before the encoding is settled** — "the contract says so" pins a sentence; only a probe pins the cell. (Sibling of the older "pinned source path ≠ pinned behavior" — this is "pinned prose ≠ pinned semantics".)
- **Route a follow-up fix to the delegate that wrote the code — resume it, don't respawn.** Both mt-069 escalation fixes went via `SendMessage` to the still-warm mt-065/mt-067 agents whose beads had introduced the code being fixed: the discriminator author picked the `ChoiceTable` seam in one step (it already knew why re-deriving resolution is forbidden), and the steps-scope author placed a one-arm fix with a solve-level pair test, each in under 20 minutes with zero re-derivation. Two warm agents also ran fine *in parallel* on disjoint files — but note one wrinkle: their gauntlets raced (one saw the other's mid-edit clippy failure); harmless here because each re-verified after both landed, but tell parallel delegates whose gauntlets overlap that a transient failure in a file they never touched means "re-run at the end", not "investigate".
- **Never mutate shared working-tree state (stash/checkout/clean) while delegates have edits in flight.** A coordinator background command wrapped a sweep in `git stash -u` … `git stash pop` "to keep the baseline clean" while two fix agents were actively editing — pure luck made it a no-op (the agents hadn't written yet; and the already-built release binary never needed a clean tree in the first place). Had the timing differed, the pop would have raced or conflicted with live agent edits mid-write. Rules: (1) the coordinator's verification commands must be read-only with respect to the working tree whenever any delegate is running; (2) before reaching for stash, ask what actually needs the clean tree — a compiled binary plus committed data files usually needs nothing; (3) if a truly clean tree is required, wait for the delegates or use a worktree.
- **The record-don't-fix escalation rule makes probe-volume delegation safe — and the warm-agent handback makes it cheap.** mt-069's sonnet delegate ran 5 workstreams and 9 probe cells under one absolute rule: a probe refuting shipped behavior is recorded as STOP-THE-LINE evidence (fixture, prediction, verbatim output, filed in Ledger/LIMITATIONS/reference) and never fixed in-bead. Result: two real divergences arrived as clean, decision-ready packets; the tech lead decided fix-now in minutes and the warm authors closed both same-session. The alternative — a volume delegate "helpfully" patching semantics mid-sweep — would have coupled an unreviewed rule change to 500 tool calls of unrelated diff. Pair the rule with an explicit deliverable shape for escalations, and the deliberately-blocked delegate stops being a bottleneck.
- **Effort-budget defaults are a measurement, not a judgment call.** The gauge's first defaults (200k conflicts / 50M encode units — "the official gauge should try hard") let single corpus commands grind >10h CPU with zero additional findings; every real discovery came from the cheap early sweep. Pick harness defaults by measuring the corpus's cost distribution (minutes for the sweep, flags to scale up), and treat a >10× wall-clock regression from a "more thorough" setting as a bug in the setting.

- **Frontend delegates must drive a real browser, and the reviewer must eyeball the pixels — Rust tests cannot see a UI bug.** All three mt-075 slices had the delegate smoke its work in headless Chrome (dump-DOM + CDP + screenshots) over live `mettle serve` fixtures; every slice caught real presentation bugs that the full green Rust gauntlet was structurally blind to (`[hidden]` outranked by pane display rules; CSS custom properties evaluated outside their scope rendering every node black; a tall drawing squeezed to an unreadable ribbon). The pattern that worked, now standing for any UI bead: the spec requires a browser smoke over named fixtures in both themes, screenshots land in a path the tech lead can `Read`, and the review includes an actual eyeball — "the tests pass" is not a review of a page. Hygiene wrinkle: backgrounded smoke servers orphan easily (two survived slice 1 parented to init); the spec should say "kill your servers, then prove it" and the coordinator should `pgrep` at review.
- **Splitting one write into several is a behavioral change even when the bytes are identical — review delegate diffs for I/O-boundary invariants, and treat "passes locally, fails on CI's OS" as a race until proven otherwise.** The `--bind` bead split serve's single-call startup banner into three `write_stdout` calls so a conditional hint could sit in the middle. Same bytes, new race: consumers (the integration tests, any script) close the server's stdout the moment they've parsed the address line, and `write_stdout` deliberately maps a closed pipe to quiet exit — so a banner write landing after the close killed the server before it served anything. macOS won the race in every local run; Linux CI lost it in 5 of 16 serve tests, all presenting as connection-reset at WS handshake — nowhere near the banner. Rules: (1) when a diff touches a write to a pipe/socket/file another process consumes, ask what the *count and timing* of syscalls used to guarantee, not just what the bytes are; (2) an invariant like "this process writes stdout exactly once, before anything reads it" must be stated in a comment at the write site the moment code relies on it (it is now); (3) a cross-platform CI failure in tests untouched by the diff is a scheduling race with the diff until root-caused — read the failure's *timing window*, not the failing test's topic.
- **When a gauge policy is genuinely open, measure every candidate on the full corpus and hand the tech lead the table — don't argue adjectives.** mt-076's config-relative counting posture had three defensible shapes; the delegate ran all three against the real corpus (A: +3 matches but 3 permanent false-alarm rows; B: zero temporal matches at either setting — the feature nets to nothing; C: mismatch-free with typed softening) and reported the table plus "each is a few lines if you disagree". The decision took one read and produced a ledger entry whose Alternatives section is *measurements*, not rhetoric. Same session, same pattern at smaller scale: the smaller-enum-budget option for the slowest test was "measured and rejected because it guts the assertions". A policy fork handed upward should arrive costed; a delegate that can cheaply run the alternatives should, before escalating.
- **A registry "denied" is not a visibility verdict while a stored credential is in play — disambiguate with a genuinely anonymous request before diagnosing.** The GHCR image looked private (docker pull: `denied`) and got filed as an owner chore; the package was public all along — the local docker config held an expired `ghcr.io` login, and GHCR rejects a bad token even where anonymous access would succeed. `curl` with a fresh anonymous registry token (no local state) returned 200 and settled it in one call; `docker logout ghcr.io` fixed the client. Rule: any auth-shaped failure observed through a client that keeps credential state (docker, gh, git remotes) must be reproduced through a stateless path before concluding anything about the remote's configuration — and the first wrong diagnosis (was "package defaults private", plausible and confidently stated) went to the owner as fact, which is the actual cost.
- **A delegate that backgrounds a long run detaches it from its own wake-up path — long runs belong to the coordinator as tracked jobs; delegates get bounded work.** During the mt-079 grid, the sweep delegate twice launched a ~10-minute gauge run via its own background shell and stopped to "wait for the notification" — which never came, because the job was not tracked by its harness; the run completed unnoticed while the agent would have slept indefinitely. The pattern that worked for the rest of the campaign: the coordinator owns every long run as a tracked background script (poll-wait for any predecessor, strictly sequential runs — which wall-time measurement needs anyway — timing files per run), and the delegate is resumed afterward for the analysis it is actually good at. Rules: (1) work a delegate performs between messages must be bounded and foreground; (2) when a stopped delegate's last words are "waiting for X", check X's real process state before nudging — a resume that re-enters the same wait just stalls again; (3) a task-notification arriving while the delegate claims to be waiting is itself the diagnostic: its wait condition can never fire.

- **A pipeline's exit code is the LAST command's — piping a gate through `tail` converts every failure into "exit 0"; a completion notification for a piped command proves nothing.** Bitten twice in one session (mt-090/mt-089 stage 2): a `timeout`-killed hour-long `cargo test … | tail -5` reported success (the kill also ate the buffered `test result:` line), and a *failed* `nix build … | tail -5; echo $?` printed `0` (tail's). Both false greens were caught only by reading the output for the positive result line — which is the rule: (1) a verification gate's command never ends in a pipe; capture to a file (`> log 2>&1`) and echo the real `$?` separately; (2) "completed, exit 0" from any wrapper is not a pass — grep the log for the affirmative marker (`test result: ok`, the artifact existing) and treat its *absence* as "did not run", not "no news"; (3) when a long job's tail is missing its result line, suspect the timeout fired — check whether the wall time hit the cap.
- **Delegate turns must be bounded by wall-clock, not just scope — a foreground wait longer than ~10 minutes is exposure to every infra failure mode at once, and a report-only resume turn salvages a repeatedly-dying agent.** One session, four kills across two opus delegates: two transient API 500s and two 600s stream-watchdog stalls, every one during an hour-scale foreground wait (sweeps, workspace tests) — the work itself was fine each time. What worked: resume the same agent (warm context survives the kill); when kills repeat, send a "no tool calls — deliver the full report + name the outstanding verifications with exact commands" turn and run those verifications as coordinator-tracked background jobs (which also serialize cleanly against each other). This extends the mt-079 lesson (long runs belong to the coordinator) with the failure data that makes it non-optional, and adds the salvage protocol: an agent that died mid-verification usually has 95% of its value in its transcript — extract it, don't re-run it.

- **A qualitative claim recorded at session wrap is prose, not measurement — before a decision consumes it, trace it to an artifact, and before prescribing a fix, read the code being fixed.** ADR-0020's first version prescribed clause-DB reduction because two wrap-time sentences said the solver was "keep-all" and the mt-089 instrument had "measured the implication order" for upgrades. Neither survived contact: the solver had had LBD reduction + phase saving since mt-049 (one grep away), and the "measured order" appeared nowhere in the mt-089 artifacts — the data-extraction delegate flagged its absence, and the coordinator initially read past the flag. The mt-055 rule ("diff a fresh run, never trust prose numbers") extends to attributions and mechanisms: a wrap entry may compress "plausible inference" into "measured" without anyone lying, and the compression is invisible two sessions later. The catch cost one same-day ADR revision; acting on it would have cost a delegated bead building what already existed. Rules: (1) any "measured/pinned/proven" in STATE/TASKS consumed by a decision gets traced to its artifact first — a delegate reporting "passage not found where expected" is a stop signal, not a footnote; (2) an ADR prescribing a change to a component states what the component currently does *from the code*, cited file:line, never from memory or prior prose.
- **A per-decision O(n) sweep charges twice — its own time plus the cache it evicts from the real hot loop — so a component-share profile understates the win of deleting it; conversely, trust share tables for ranking, not for exact yield.** mt-092's heap replacement of the O(vars) `pick_branch` scan beat its own Amdahl bound on the biggest row (1.34× measured vs 1.24× "component free" ceiling): the scan streamed ~1.2 MB per decision through cache, evicting `propagate`'s working set, and that cost was billed to `propagate`'s 68.7% share. The profile still ranked the components correctly — it just could not see the interaction term. Corollary for reading any wall-share table: components that stream memory distort their neighbors' shares; deleting one can pay more than its line item, and micro-optimizing another can pay less.
- **Trajectory-neutral vs search-changing is the load-bearing split for solver work — the first gets a byte-identity acceptance bar (sweep sha256, exact conflict counts), the second gets a full row-diff with disclosed regressions, and they must never share a commit.** mt-092 ran both in one day: the arena+heap pair proved itself with a sha-identical 564-command sweep and to-the-digit conflict counts (any argmax slip anywhere in 380k conflicts would have cascaded), while blocking literals — a steady 1.13–1.46× per-conflict win convolved with a 0.1×–1.5× conflict-count lottery — turned a 0.12s row into an over-budget defer even as it netted +2. Had they shipped together, the regression triage could not have told cache engineering from search change. Second half of the lesson, from the same runs: absolute wall on this machine drifts ~1.5× over hours of continuous sweeps (thermal, not sleep — extends the mt-083 signature), so solver A/Bs interleave separate binaries with the OLD code as a live control in the same batch; a solo re-measurement after hours of load is not comparable to a morning baseline.

- **Calibration points cannot accept a search change — N rows winning big is still not a sample — and a delegate's/survey's "X by construction" property claim is a prediction until measured.** mt-093 stage 1 (trail saving): both calibration rows won dramatically (−73.5%/−18.1% conflicts, 4.85×/1.19× wall), every test green, correctness spotless — and the full 564-row diff priced the change at net −2, so it was reverted under ADR-0021's pre-authorized rule. The delegate's replay-off control had already shown why the calibration wins meant nothing: the technique's principled channel (early conflict detection) fired ~0 (6/2,333 and 20/139,624 conflicts); the wins were the trajectory lottery landing heads twice. Same stage, second half: the technique survey claimed trail saving is "trajectory-neutral by construction"; the ADR demoted that to a prediction-to-test (replayed literals carry saved reasons/levels/orders, all of which feed `analyze`) and the measurement disproved it. Rules: (1) a search-affecting change is accepted or reverted ONLY on the full row-diff — calibration rows are for wall attribution, never for acceptance; (2) any "by construction" claim imported from a survey or paper gets an explicit falsifiable prediction and a control run before it shapes an acceptance bar; (3) pre-authorizing the revert condition in the ADR (before implementation exists to be attached to) is what made the net-negative verdict a same-day one-liner instead of a debate.

- **Implementation quality is zero evidence of yield — a campaign whose stages keep measuring negative should test its grounding thesis directly, as its own cheap experiment, before (or at latest while) spending stages.** mt-093 went 0-for-3 (−2/−2/−6 on the full row-diff) with every stage implemented well: predictions-first delegates, independent adversarial reviews finding no defect, spotless DISAGREE/self-check/panic lines — and none of that correctness moved the corpus, because the campaign's causal model (per-conflict propagation volume tracks learned-clause length, ADR-0020 §(b)) was false, which stage 2's A/B demonstrated *directly on the three rows the model was derived from* (length −25…−37% while props/conflict moved −0.5/−1.4/+25.1%). That falsification cost one instrumented A/B; it was available in principle before stage 1 was specced. What made the 0-for-3 cheap rather than a disaster: the ADR pre-authorized the revert condition, every stage banked its patch + A/B harness, and each rejection was converted into a recorded model correction. Two corollaries from stage 3: (1) a disclosed structural flaw ("the core tier is an uncapped ratchet") is a *prediction of the row-diff's sign* — when the delegate names one before the verdict, weight it over the calibration trio's split; (2) fixing a genuine defect can make results *worse* when the defect was throttling a flawed mechanism (the level-0 LBD-convention fix fed the ratchet harder, +65% conflicts on ertms) — a large metric swing from a one-line convention fix is fragility evidence about the mechanism, not a reason to un-fix the defect.

- **A rule generalized from one cell family is a hypothesis, not a pin — before a contract amendment ships, probe the family × context matrix, and re-probe the banked cells the new rule would have to overturn.** mt-095's wave saw union-nested casts shed the overflow guard (k4/k16) and the tech lead amended LEDGER-010 to "a cast reached through *any* set former sheds"; one chunk later mt-096's 36-cell former × reader matrix showed mettle already matched the jar on 26 cells and the amendment would have regressed 12 — the jar keeps the guard through intersection/difference/ITE/join/override/product, and even the union's shedding is context-dependent (t4c vs t4e: the identical union shape guards with no quantifier and sheds under one; two capable casts guard). Three successively narrower candidate rules each died to a cell, one *after* being implemented and measured — and the killing cell came from re-probing mt-051's banked T1/T4 against the live jar rather than trusting them (the banked expectations held; the candidate would have broken green tests). Rules: (1) an amendment whose evidence is one syntactic family gets the matrix (family members × readers × contexts) before it ships, not after; (2) any candidate rule that would flip an existing green probe-cited test must re-run that test's jar cell live before the rule is believed; (3) when no predicate over your IR separates the observed cells, the honest outcome is a conservative pin with the matrix recorded — a wrong rule in the ledger costs more than a documented divergence, because delegates implement *from the ledger*; (4) the direction of the conservative default matters — prefer the side that can only under-accept vs the jar (jar-SAT→mettle-UNSAT), never the side that could fabricate an instance.

- **A ✔ ledger entry can be silently destroyed by an adjacent doc edit, and every stale forward-pointer to the bead then becomes a re-cut trap — before cutting any bead from a "filed as mt-NNN" pointer in an old record, run `git log --oneline --all -S 'mt-NNN'` first.** mt-085 shipped 2026-07-29 (`b79c108`), and the very next doc commit (`2896e2a`, mt-086, same afternoon) accidentally REPLACED its ✔ TASKS entry instead of inserting above it — the diff shows `- ✔ mt-085` / `+ ✔ mt-086` as one hunk. Nothing noticed for three weeks because ✔ entries are history, not work drivers. The damage surfaced 2026-08-21: mt-084's record still said "needs its own probe round, filed as mt-085" and STATE's availability lists still said "mt-085→mt-027" — both true when written, both stale within hours — so the coordinator re-cut mt-085 as a fresh bead and delegated it. The delegate caught it (searched git history before re-probing, found the commit, verified the shipped tests still pass live: 28/28 + a 33/33 jar re-run) at the cost of one spec message instead of a duplicated multi-hour probe round. Rules: (1) a "filed as" sentence in a ✔ record is a POINTER, not a status — check the pointee's real status in git (`-S`) before acting on it, because TASKS/STATE prose can lose entries while git cannot; (2) when closing a bead that an earlier record forward-references, amend that record's sentence in the same commit ("closed — see ✔/sha"), so the pointer can never outlive its truth; (3) when editing a Done section, the diff hunk must be checked for what it REMOVES, not just what it adds — an insertion that lands as a replacement is invisible in the added lines; (4) a delegate that answers a task spec with "this is already done, here is the commit" is doing exactly what the spec's outcome-honesty clause asks — the same class of finding as contradicting a fabricated constraint (see the mt-055 lesson above).

- **A measurement harness is itself an instrument that needs calibration — classify outcomes by their full signature (exact rc, signal sign, stderr text, wall time), never by a boolean cut, and treat a suspiciously uniform or suspiciously extreme row as a harness bug until proven a finding.** mt-021's threshold round hit three traps in one afternoon, each of which produced a confidently wrong table: (1) `cmd | head` reports `head`'s exit code — a crashing probe read as rc=0; (2) Python's `subprocess` reports signal deaths as NEGATIVE returncodes (`-6`, not the shell's 134), so an `rc < 128` "survived" test scored every crash as survival and produced an all-clean matrix; (3) a timeout returned `None`, and `if not survives(...)` treated `not None` as "crashes" — fabricating a "crashes at 500" row that drove a 6× too-tight bound (125 vs the correct 768) into the draft arithmetic. The row was caught not by re-running but by a *mechanism* smell at review: the shape was right-associative, so the existing nesting guard should have produced a typed error there — and chasing that mismatch surfaced a real pre-existing hang (mt-103) the boolean harness had been hiding. Rules: (1) every probe result records rc, signal, stderr tail, and wall time — the classifier reads the tuple; (2) hangs are a distinct outcome class, never folded into "crash" or "survive"; (3) when a measured row contradicts the known mechanism of the code under test, adjudicate the contradiction BEFORE using the row — it is either a harness bug or a discovery, and both matter more than the table; (4) fourth trap from the same bead's gate, filed with mt-097's pattern: hash comparisons over generated artifacts must path-normalize and sort first — a raw sha differs between any two runs because output paths are embedded, and reads as a false gate failure.

- **A delegate's silence is an observability gap, not evidence of a stall — check the tree before respawning, and require phase-completion heartbeats on long beads.** During mt-021 the delegate went ~5h without a report while legitimately grinding multi-minute jobs (a thrice-re-run threshold matrix, a 150,891-code scan, cliff bisections); the coordinator read the silence as a death, spawned a recovery agent onto the same tree, and only the delegate's own unconditional tree-check-before-editing (it held on an unexpected TASKS.md edit — which was the coordinator's own committed bead-cut) kept two writers from colliding. Rules: (1) before respawning over silence, check the work products (probe dir timestamps, git status) — a warm tree means wait or nudge, not respawn; (2) if a recovery agent IS spawned, stand it down the moment the original revives, before it edits; (3) long-bead specs include "send a heartbeat to main at each phase completion"; (4) the delegate-side discipline generalizes: on resuming after any gap, re-verify the tree against your own last-known state and report any edit you didn't make, even when its content looks plausibly legitimate — accuracy is not authorship.

## Reference / oracle gotchas (summary; full detail in [reference/alloy6-reference.md](reference/alloy6-reference.md))
- Alloy 6.2.0's integer-overflow default **differs by entry point** (GUI forbids, headless allows). Never assume a default — set it explicitly. → [LEDGER-001](../SEMANTICS_LEDGER.md).
- The `exec -y/--ymmetry` CLI flag is a **no-op** (upstream aliasing bug); set `symmetryBreaking` via the `A4Options` Java API instead. → bead mt-006.
- `exec` litters an output directory named after the model into the CWD; run the harness in a temp workdir and force `-s sat4j` for zero native deps. → bead mt-006.
- **A pinned source path is not pinned behavior — gating/optimization code you read in the translator may be dead on the jar's actual solve path; pin every conditional by a decisive probe before implementing it.** mt-048's contract faithfully transcribed `Translator.translate`'s `retainAll(formula.relations())` + `usesInts`-gated `ints().clear()` from the static source — and all of it is a dead letter under the entry path the pinned jar actually takes (Pardinus/incremental): three probes (unmentioned-sig Y6, `univ`-field uf1-SB20, string fmrun) showed nothing is mention-gated and every int **and string** atom is a permanent singleton class (the per-atom `s2k` exact singletons cover padding atoms too). The delegate implemented the transcribed-but-dead gating; the missing string singletons produced 6 of the 9 SB-20 count mismatches (fm2cfs), and the `usesInts` walker was pure dead code — deleted at review. Discipline: for any *conditional* behavior lifted from source (a gate, a cleared collection, an optimization guard), design the probe that would fire **only if the condition is live**, and run it before the contract ships; "the code says so" pins the *mechanism*, only a probe pins the *reachability*. Corollary, same day: a review probe aimed at one hypothesis can strike something else entirely — the `univ`-field probe was built to test symmetry-detection gating and instead surfaced mt-053 (live-`univ` vs all-atoms), a pre-existing wrong-verdict candidate invisible to every corpus gauge; when a probe's numbers disagree BEFORE the machinery under test even engages (the SB-0 side diverged), stop and root-cause the baseline first — that divergence is the finding.
- **A "cached immutable fact" is only immutable if its capture config had no wall-clock edge — record the boundary cases at a generous timeout, in a supplementary file, not by editing the primary.** mt-054's count-baseline capture reproduced the live SB-20 net exactly, but the SB-0 net came back 47/49: two `chordbugmodel` copies sat near the 300s per-file JVM boundary and timed out during capture where the live run had completed. The counts themselves are immutable; *whether a 300s run produces them* is not. Fix pattern: identify the boundary files from the net's `per_command` delta, re-capture only them at 3× the timeout into a `*-slow-*` supplementary baseline (the loader's sorted-name/later-wins merge exists for exactly this), and leave the primary untouched — after which the cached net reproduced the live results bucket-for-bucket. Corollary: when a cached sweep's buckets differ from the live-era numbers, suspect the wall-clock-adjacent buckets (`timeout`, `over_budget`) first, and triage by diffing per-command dispositions, not totals.
- **"Absent from the mismatch list" is not "verified match" — a hard constraint handed to a delegate must trace to a positive baseline entry, not a report's silence.** At mt-055 the tech lead told both root-cause agents that the diverging commands "match exactly at SB-0" — inferred from the SB-0 net's empty mismatch rows. The actual baseline entries were a file-level `timeout` (tso) and the `10001` cap sentinel (wetdry): those commands never reached comparison at all (mettle-side typed skips and jar-side timeouts both bypass it), so the "constraint" was fabricated. It misdirected one investigation ("don't chase semantics theories") until the agent's own evidence contradicted it — and the agent did the right thing: flagged the contradiction against the given constraint instead of smoothing it over, which is what surfaced the error. Rules: (1) before pinning a "hard constraint" into a spec, read the underlying baseline/artifact entry for the specific command, not an aggregate report; (2) a typed skip is an *absence of evidence*, and the buckets that eat evidence (`timeout`, `enum_budget`, `mettle_cap`) must be checked by name before claiming any per-command fact; (3) a delegate contradicting a spec-stated "established fact" with primary evidence is a finding, never insubordination — the spec should invite it explicitly.
- **When two subsystems each pin a convention about the same name, the contradiction stays latent until the first input exercises both — grep for the assumption when pinning the second.** mt-030's bounds builder named root-module relations bare (its own test docs said so); mt-048's §16.3 SBP contract *assumed* names carried the jar's `this/` prefix. Nothing failed for ten beads because no corpus model mixed root- and opened-module relations at the same arity in the SBP sort — until wetdry, where the sort order silently inverted and under-broke symmetry (888 vs 784; the discriminating lex bits fell past the cap). The root cause was found by dumping the jar's ground-truth names (`A4Solution.debugExtractKInput`) rather than trusting either mettle convention. When a contract doc asserts "X already holds," verify it with one probe before building on it — and when adopting a convention fix, prefer making the name *actually* match the jar everywhere over a local shim at the consumption site (the same wrong name will be consumed again).
- **A file-level oracle timeout is not evidence about per-command hardness — always probe per-command before writing a file off as non-comparable.** correctChord was "the one file the jar itself cannot sweep even at 7200s" (mt-057) and stood as permanently non-comparable for four days — yet at mt-083, run one JVM per command, 36 of its 39 commands answered (most in 2–75s; a handful of pathological commands had dominated every serial whole-file run). The banked verdicts immediately exposed 5 real mettle wrong verdicts that "nothing to compare against" had been hiding. Generalization: a serial timeout localizes to the *unit of execution*, not the members; shrink the unit before accepting a coverage hole — especially when the hole is exactly where wrong verdicts could hide.
- **Laptop sleep silently breaks `timeout`-wrapped long runs: real-time alarms don't fire while asleep, so every pending cap fires at wake, uniformly inflating elapsed figures (and letting "capped" children run far past their budget).** Seen at mt-083 tier-1: four concurrent 900s-capped JVMs all reported ~2788s. Verdict-style results survive (deterministic budgets, an answer is an answer) but wall-time data is contaminated and worker slots stay occupied. Rule: `caffeinate -is` (time-bounded) wraps any coordinator background run longer than a few minutes; suspiciously *uniform* elapsed times across concurrent jobs are the sleep signature.
- **A typed budget defer can hide a wrong verdict indefinitely — an independent stronger solver on the same encoding is a cheap, oracle-independent audit of the defer tail.** For the whole conversion campaign, `correctChord[28]`'s spurious UNSAT sat invisibly behind `over_budget`: every budget probe (25k→1M conflicts, mt-078/082/088) stopped before the wrong answer was reachable, so DISAGREE 0 kept reading as "no wrong verdicts" when it actually meant "no *reachable* wrong verdicts." The mt-089 CaDiCaL instrument — same CNF, stronger search — pushed through on its first run and exposed it (jar SAT / mettle UNSAT, the ADR-0012 overflow-polarity rule mishandling an antecedent-position cardinality comparison; → mt-090). Rules: (1) verdict claims are conditioned on reachability — say "DISAGREE 0 *at these budgets*", and treat the defer buckets as unaudited space, not clean space; (2) when a second solver exists for any reason, running it over the defer tail is a near-free wrong-verdict sweep (verdicts are backend-independent; any cross-backend difference on one encoding is a bug by construction); (3) a "stuck at every budget" row that suddenly *answers* under a stronger engine deserves suspicion before celebration — check it against the oracle before banking it as a conversion.
- **A probe fixture's field defaults to `one` multiplicity — every "is it empty?" leg over `sig F { v: Int }` is vacuously UNSAT and tells you nothing; declare `set` explicitly when emptiness is the question.** mt-052 lost its whole first verdict round to this: `sig F { v: Int }` means `v: one Int`, so cells asking whether a probe expression denotes the empty set could never distinguish the hypotheses. The paired trap from the same round: comparing against a spelling that is itself the artifact under test (`0-7` as "−7" — it is the set `{0}`). Rules: (1) any emptiness/cardinality leg gets a `set`-typed carrier field; (2) every comparison target in a probe is itself probed (or a `fun/…` form) before it anchors a cell; (3) when a round's cells come back suspiciously uniform, audit the fixture before the hypothesis — the delegate that caught both did so by re-deriving what round 1 *could* have distinguished, and re-ran only the invalidated legs (documented in `scratchpad/probe/mt052/NOTES.md`).

## A gate's cost is a measurement, not a memory (mt-109, 2026-08-23)
Three consecutive sizing chunks (mt-104/106/108) planned around "no cached jar verdicts survive and a full 150k jar sweep is the expensive one-time gate" — inherited from the per-file-JVM era. The mt-109 delegate simply re-ran it: the batch `ResolveGaugeShim` covers all 150,891 codes in ~225 seconds. The stale cost assumption shaped bead sequencing, gate design, and an "estimate instead of measure" fallback for two rounds. Rule: before treating any gate as expensive enough to plan around, time it on the current tooling — and when a cheap re-measure would replace a prose-derived number, run it. (Same family as the "diff a fresh run, never trust prose" rule; this is its planning-cost twin.)

## A pinned rule built on a literal string is a namespace clue, not a mechanism — ask what could produce that string before accepting it (mt-118, 2026-08-24)
The mt-118 probe round behaviorally pinned the eq-redundant non-firing on the train models (`029361–029370`) to fields whose declared name is literally `pos`: 24 probes, 91/91 corpus cells confirming the pattern, clean discriminating controls (non-`pos` fields warned normally) — a genuinely careful validation campaign — and it still prescribed the wrong fix, a name-string carve-out for `pos` in `same_expr`. One cheap follow-up probe broke it: fields named `neg` and `zero` suppress the warning identically, and a field named `f` does not. The real mechanism was never about the string `"pos"` at all — `util/integer` auto-opens into every module and exports `pos`/`neg`/`zero`/`min`/`max`/… as funs/preds, so a field sharing any of those names is invisibly overloaded even when declared exactly once in the model, which is what triggers the reference's choice-identity non-firing (§5 item 9 of [reference/warning-parity.md](reference/warning-parity.md)). Two things generalize: (1) when a pinned rule's predicate is a literal string or magic constant rather than a structural property, ask what *namespace* could produce that literal — stdlib auto-opens, reserved words, builtin overloads — before accepting the rule as the mechanism, not just after it breaks; (2) validation volume cannot rescue a biased corpus — 91/91 was a real number, but every one of the 91 training-model instances happened to use the field name `pos`, so no amount of re-confirming against that same population could have distinguished "the string `pos`" from "anything colliding with `util/integer`'s exports." The fix that shipped came from designing the one cell that would split the two hypotheses, not from running more of the same cell.

## A probe wave pins only the positions it wrote cells for (mt-111, 2026-08-23)
The mt-109 mult wave (88 cells, predictions-before-runs) probed `exactly` only as an expression prefix, found it never parses there, and concluded the exactly-of reject was source-unreachable — flagging its own guess honestly (§2.5) but still guessing. Implementation refuted it: the reachable spelling is a quantifier decl written `x = e`, worth 13 of the family's 38 codes, found only because the residual differential after the first pass still held 13 codes with the literal message and the delegate probed the jar instead of massaging the estimate. Two lessons that generalize: (1) a message-class bucket in the triage is evidence the spelling IS reachable — "unreachable" plus a nonzero bucket means the wave's cell matrix missed a producer, not that the label is wrong; (2) the implementation sweep is a backstop for the probe wave only if a residual mismatch triggers fresh jar probes rather than a shrug — budget for one mid-implementation probe round in any family whose rule was pinned from an adversarial matrix. Corollary from the same day (mt-110/mt-111 both): the committed jar-verdict baseline turned the reject-direction gate from a ~20-min jar+sweep affair into a ~1-min diff, which is what made "probe the jar again mid-implementation" cheap enough to actually happen.

## Bank raw grids, not just conclusions — a decision day may need them years of context later (mt-119/120, 2026-08-24)
The compute-tail sizing (mt-119) answered every per-row question — which of 49 deferred rows convert at which budget, on which axis, with which anomalies — **entirely from grids banked by earlier campaigns** (mt-088's census, mt-092's grid + cross-run), with zero new sweeps. That made the whole decision chain (sizing → owner reopening the solver posture → ADR-0027 → spike GO) fit in one day. The conclusions those campaigns wrote in prose would not have sufficed: the deciding facts (elevator[18]'s conflicts-bound regression at the 100k×256M point; capacity rows' zero conflict sensitivity) were *in the raw per-row JSONs*, never in any summary. Corollary from the same day, other direction: a criterion you assumed independent may be a dependency — the mt-120 spike found count parity (criterion 2) unmeasurable without effort observability (criterion 3) because an `enum_effort_budget ⇒ reports_effort` assert *panics* and destroys the stage-1 verdict too; gate lists deserve a dependency check, and capability gaps should be typed refusals, never asserts on a path data can reach.

## A pinned CI runner label is a dependency with a retirement date — verify it against the release pipeline's *actual* labels before waiting on it (mt-124, 2026-08-25)
The cross-target battery's Intel-mac leg queued for over an hour against `macos-13` — an image GitHub retired in December 2025, eight months before the run. The hand-written workflow had pinned the label when it was written and nothing ever exercised it (the battery had never run on a tag — its own recorded debt). The unblock came from asking what the *release pipeline* actually uses: `gh api` on the last successful release run showed dist 0.32.0 already building `x86_64-apple-darwin` on `macos-15-intel`, so the fix was both known-good and alignment-improving (the battery now runs the exact runner that builds the release artifact). Three things generalize: (1) an infinite queue with an empty `runner_name` means "no such pool", not "busy" — check the label's existence before waiting on it; (2) when two workflows must agree on an environment, derive the pinned label from the authoritative one (query its last real run) instead of writing the same constant twice; (3) hosted-runner labels are dependencies with retirement dates — when one appears in a workflow, record its horizon (`macos-15-intel` retires fall 2027, and the x86_64-apple-darwin release target retires with it unless an ADR decides otherwise).
