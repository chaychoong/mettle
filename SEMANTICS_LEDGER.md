# Semantics Ledger

**Status:** living document · **Owner: human (product owner).** Agents implement *from* this ledger; they do not author settled rules into it.

## Purpose
For every corner where the reference Alloy jar's behavior *is* the spec, this ledger records a **one-sentence behavioral rule** plus a link to the conformance test that pins it. This is the understanding the project exists to produce. The rule is: read the reference until the behavior can be stated in one sentence, verify it empirically against the pinned jar, write it here with a test, then implement idiomatically.

## Entry format
```
### LEDGER-NNN — <corner>
Rule: <one sentence, testable>.
Status: proposed | verified | approved
Evidence: <how it was checked against the pinned jar>
Test: <path to the conformance test>
```
- `proposed` = drafted by an agent/tech lead, **not yet human-approved**.
- `verified` = confirmed empirically against the pinned jar, **with no open residual uncertainties** — every soft spot the drafting work flagged has been probed shut (or has amended the rule).
- `approved` = product owner has blessed it as canonical. **Only `approved` rules are safe to implement against.**
- Process rule (owner, 2026-07-16): an entry is put to the owner for approval **only at `verified`** — never with "re-derive later" caveats attached. If stating the rule wrong is a risk, the answer is more probes, not a caveated sign-off.
- Process rule (owner, 2026-07-18 — "Option B"): **no-fork entries** — entries that merely restate verified jar behavior with no genuine decision fork — are approved by the **tech lead** once `verified` (recorded as `approved (tech lead, no-fork delegation)`). Owner approval is reserved for entries containing a **genuine fork**: jar ambiguity/inconsistency (LEDGER-001's class), a deliberate divergence from the jar, or a resource/scope tradeoff. The tech lead must flag any fork explicitly and bring it to the owner framed as a decision with consequences — never buried in a status report.

### LEDGER-001 — integer overflow default ("forbid overflows" / `noOverflow`)
**Rule:** mettle treats integer/cardinality arithmetic exceeding the bitwidth as **forbidden by default** — an overflowing term excludes the instance (matching the Alloy GUI's default "Prevent overflows" = on). A `--[no-]overflow` flag switches to allow/wraparound semantics.
**Status:** `approved` (product owner, 2026-07-15). Facts below `verified`; safe to implement against.
**Evidence:** Alloy 6.2.0's default is **entry-point-dependent** (verified 2026-07-15, see [reference/alloy6-reference.md](docs/reference/alloy6-reference.md) §3(c) — reproduced by tech lead): GUI default = forbid (`noOverflow=true`); headless jar / `A4Options` default = allow/wraparound (`noOverflow=false`). Decisive test: `run { plus[7,7] < 0 } for 4 int` → **SAT** (allow) by default, **UNSAT** under `-n` (forbid). Default bitwidth = 4 (range −8..7).
**Decision (approved 2026-07-15):** canonical default = **forbid overflow**, to match the Alloy GUI's default experience (the Alloy users actually run). The conformance harness sets the oracle's `noOverflow` to match mettle's active setting so the scorecard always compares like-for-like.
**Test:** _(added with the Rung-3 integer work)_

### LEDGER-004 — `util/ordering` exact bounds & order pinning
**Rule:** The pinning **trigger is the reserved `pred/totalOrder[S, F, N]` keyword** (a context-sensitive grammar token — string-matched spelling, pre-resolution), NOT the `util/ordering` module identity: any `one` sig whose own appended fact carries the reserved call over its own two fields gets the treatment, with the module header, filename, sig name, and field names all irrelevant (mt-041 probe matrix rows 2–5), and the semantically identical order spelled without the keyword getting nothing (row 6). `util/ordering` is simply the one stdlib file using the keyword, and its fact is exactly as reachable when the file is **run as the root module** as when it is opened. Exactness of `S` comes from the separate, general `exactly`-param mechanism: opener bindings (`additionalExactScopes`) — or, for a parametric module run as root, the header's own `exactly` marking forcing the materialized param sig exact **at header level**, independent of the command's scope clause (row 7). Given the trigger and an exact `S`: **(a)** when `S` has no proper subsig, or its subsigs leave no partition choice, the order's `first`/`last`/`next` are bound to exact constants over `S`'s atoms in universe order (`first = S$0`, `last = S$<n-1>`, `next` = the consecutive-atom successor) — the linear order is fully pinned, independent of the symmetry-breaking setting. **(b)** When `S` has a proper subsig with non-exact scope, or two-or-more subsigs (even if individually exact), the constant binding does **not** engage: `first`/`next`/`last` are governed only by the ordinary `pred/totalOrder` constraint, and genuine order freedom (which chain rank carries which subsig tag) survives as multiple distinct instances at every symmetry setting.
**Status:** `approved` (product owner, 2026-07-16, on the amended two-part rule; **trigger re-keyed 2026-07-24 at mt-041, tech-lead approval under the Option-B no-fork delegation** — pure match-the-jar, no behavioral fork: the eligibility conditions (a)/(b) are unchanged, only the detection trigger was corrected from "opening `util/ordering`" to the reserved-keyword rule, closing the root-module count divergence the exit gate named). Documented conservative boundaries (verdict-safe — the hand-built `pred/totalOrder` formula always still governs where pinning does not engage): a module-level fact spelling the fields by explicit qualification (`Ord.First`) is deliberately not matched (unprobed, zero corpus incidence); the reserved keyword over a genuinely non-exact `S` does not pin (`lower == upper` gate in `pin_ordering`).
**Evidence:** probes T4/T4b plus the mt-028 exhaustive matrix T10-T19 in [reference/alloy6-translation.md](docs/reference/alloy6-translation.md) §5/§10.1 (jar-verified 2026-07-16, OpenJDK 21, `oracle/org.alloytools.alloy.dist.jar` 6.2.0); the mt-041 trigger matrix §10.1b rows 1–7 (jar-verified 2026-07-24, JDK 21 via the flake) with source pins at commit `794226dd`: `Alloy.cup:146`/`383–390`, `ExprList.java:213–222`, `TranslateAlloyToKodkod.java:1069–1077`, `CompModule.java:1270–1298` (`addModelName` root path). Confirms: instance count = 1 at both symmetry 20 and symmetry 0 for a childless ordered sig at every tested size 2-6 (T10a-e), `next` always the plain consecutive chain `S$0->S$1->...->S$<n-1>` (resolves the old ">3-atom orders" residual); two independent ordered sigs pin independently (T12); an enum auto-opens ordering with the same pinning, `first` = the first **declared** constant (T13); the pinning is triggered purely by the `open` even when `first`/`next`/`last` are never referenced in the command (T19); a conflicting fact on `first` is UNSAT, proving the binding is a genuine constant not a solver preference (T16); a `var` ordered sig is rejected at parse/resolve with an explicit message (T18).
**IMPORTANT — the matrix also found a genuine counterexample to the rule as stated** (T14a-e, T15; resolves the old "partially scoped ordered sigs" residual, §9): when the ordered sig `S` has a proper subsig with **non-exact** scope, or **two-or-more** subsigs (even if each is individually `exactly`-scoped), the exact-constant shrink on `first`/`next`/`last` does **not** engage — `pred/totalOrder` is instead solved as an ordinary constraint, and genuine order freedom (which chain rank carries which subsig tag) survives as multiple distinct SAT instances at **both** symmetry 20 and symmetry 0 (e.g. T14b: 3 instances at sym20, 6 at sym0, all sharing the identical atom-name population `{A$0,A$1,B$0}` but with `B$0` at a different chain rank in each). The sig's **overall exact-scope forcing** (part (a) of the rule) is unaffected and holds unconditionally in every subsig configuration tested; only the **exact-constant** binding of first/next/last (part (b)) is subsig-conditional. An unrelated field reference to `S` (not a subsig) does not trigger this — T15 is a clean isolating control.
**Rule history:** the original mt-028 draft stated only the childless-sig behavior ("forces exact scope + binds first/last/next to exact constants, unconditionally"); the T14/T15 probes showed the constant-binding half is subsig-conditional, and the 2026-07-16 amendment added part (b). The 2026-07-24 mt-041 amendment corrected the **trigger**: the original framing ("Opening `util/ordering[S]`…") described the common instance, not the mechanism — the jar's trigger is the reserved `pred/totalOrder` keyword (`Alloy.cup:146`/`383–390` → `TranslateAlloyToKodkod.java:1069–1077` → Kodkod's native TotalOrdering predicate) plus the general `exactly`-param exactness machinery incl. its root-module header path (`CompModule.java:1270–1298`). mt-035's implementation had keyed on module identity (a proxy of the then-correct §5 source note) and diverged exactly where the proxy and the mechanism differ: the module run as its own root (the SB-0/SB-20 counting nets' only mt-041 mismatch family, now retired). Probe evidence: translation-ref §10.1b (rows 1–7, jar-verified 2026-07-24).
**Test:** `crates/als-core/tests/solve.rs` — the `ledger004_*` suite (mt-035: plain-sig exact-shrink path AND the subsig fallback path as two distinct behaviors) plus the `mt041_*` suite (root-module pinning = 1; identity-independence; row-6 no-keyword negative control = n!; row-7 header-`exactly` forcing incl. the `#elem = 2` UNSAT; subsig-of-one-parent non-pinning with its positive control).

### LEDGER-005 — integer wraparound & bitwidth (arithmetic at bitwidth)
**Rule:** At bitwidth `w` (default 4, signed range `−2^{w-1}..2^{w-1}−1`), the `fun/…` operators (`plus`/`minus`/`mul`/`div`/`rem`, shifts `<<`/`>>`/`>>>`, unary negate, `sum x|ie`, integer if-then-else) evaluate in `w`-bit two's-complement — **`div` truncates toward zero, `rem` takes the sign of the dividend, `<<` is logical-left, `>>` arithmetic-(sign-extending)-right, `>>>` logical-(zero-fill)-right** — and, in **allow** mode, **wrap** silently; the surface `+`/`-` are relational union/difference (no int↔Int coercion), so arithmetic is reached only through the `fun/…` forms — with **one pinned syntactic exception** _(dated **mt-052 amendment**, tech lead, 2026-08-21)_: a literal `0 - (max+1)` at the command's bitwidth folds to the int **constant `min`** — an `IntExpression`, int-sorted everywhere the jar dispatches on the translated Kodkod class (it renders bare in the evaluator, drags an ITE to the int branch, and feeds `toInt` unwrapped). The guard is purely syntactic on the resolved AST: parentheses are transparent; a computed `max+1`, a `let`-bound one, a non-zero LHS, and any other RHS all stay set difference; the trigger literal moves with the scope (`0-1`@bw1 … `0-16`@bw5). Full pin: translation-ref §10.7i, probes C01–F06 (`scratchpad/probe/mt052/`); this is also why `(0-8)` is the clean MIN spelling where `negate[8]` carries a permanent overflow flag (§10.7d's audit). `div[x,0]` (allow mode) is now a fully closed form: **`div[x,0] = -sign(x)`** — `1` for every negative `x` including MIN, `0` at `x=0`, `−1` for every positive `x`; separately, `div[MIN,−1] = -8` (ordinary two's-complement division-overflow wraparound, correcting an earlier probe-spelling artifact that had this at `1`). **Shift-amount masking (pinned mt-044 round 3, §10.7d):** the shift amount for `<<`/`>>`/`>>>` is masked to its low `⌈log2 w⌉` bits before shifting (source: `TwosComplementInt.shl`/`shr`, `32 - Integer.numberOfLeadingZeros(w-1)`, confirmed at bw3/4/5/6 with no discrepancy — a closed bit-length identity, not width-specific); `>>`/`>>>` **never self-overflow** on any operand (own overflow bit hardcoded `FALSE` in source, only pre-existing operand overflow propagates); `<<` sets a genuine overflow flag when the shift truly changes the represented value, but has a **jar-specific defect**: a masked-away ("junk") high bit of the shift amount can spuriously set the overflow flag with zero effect on the actual shifted value, depending on the shiftee's own bit pattern at the position the jar's incremental barrel-shifter circuit happens to inspect for that bit — mettle must replicate the jar's exact per-bit circuit (not just "did the masked value change") to stay bug-compatible; full per-op conditions and decisive probes in §10.7d. In **forbid** mode (mettle's LEDGER-001 default) an overflowing subterm does **not** flatly conjoin `¬overflow`; at the comparison where an `Int` becomes a `Formula` it is guarded by the **Milicevic/Jackson polarity rule** (`DefCond.ensureDef`): at positive polarity an *existentially*-dependent overflow forces the atom **false** (`∧ ¬of`, excluding an overflowing witness) while a *universally*-dependent overflow forces it **true** (`∨ of`, so a `∀` is not falsified by an overflowing binding); negative polarity swaps the two. **Caveat, pinned mt-044/§10.7c–§10.7d (2026-07-19, three follow-up rounds same day — gap-closing, then a shift-semantics + `negate[8]`-confound audit that retracted half of the second round's own finding):** the guard reliably fires for single-quantifier formulas over `Int`/`seq/Int`, and is **conclusively independent of Kodkod's `skolemDepth`** (swept 0 through 4 and off — identical at every value, refuting the original skolemization hypothesis). There is **one** defect, not two: `DefCond.isInt` recognizes *only* the literal bare `Int`/`seq/Int` builtin as "an Int domain" — any quantified variable whose **own** domain is anything else (a comprehension, or a **sig**) has its classification silently default to existential, **unconditionally, regardless of nesting depth (0, 1, 2, or more) or nesting shape (lone `∀`, same-type `∀∀`/`∃∃`, or mixed-type `∀∃`/`∃∀`)** — invisible when the variable is genuinely existential, wrongly excluding-instead-of-rescuing when it is genuinely universal. **This is a live, practically significant wrong-verdict risk**: `all p: SomeSig | <cardinality-overflow comparison over p>` — the single most common corpus shape this entry touches — is confirmed (decisive jar probe: forced-nonempty-field cardinality under a bare `all p:P`, `plus[#p.f,7]>=0`) to get **forbid = UNSAT (excluded)**, not the naive rule's SAT (rescued), with the identical arithmetic shape driven by a bare-`Int` `∀` confirmed to rescue correctly as an isolating control. **A second, independent "nesting-position" defect was reported in the gap-closing round and is RETRACTED here**: every one of its decisive probes turned out to spell an enclosing universal's domain lower bound as `negate[8]` (`=minus[0,8]`, itself an overflowing computation carrying a permanent forbid-mode overflow flag — confirmed: `negate[8]=negate[8]` is forbid-UNSAT, `(0-8)=(0-8)`, the clean peephole-folded MIN literal, is forbid-SAT), which silently forces any `x>=negate[8]` domain guard false for every candidate, **emptying the whole domain** and producing vacuous-truth verdicts (`all n:{empty}|BODY` trivially SAT, `some n:{empty}|BODY` trivially UNSAT) that mimicked a nesting-position effect. Re-probed with the clean `(0-8)` bound, every one of those cells — including the same-type `∀∀` nesting, previously (and wrongly) reported as evidence that same-type nesting is inherently robust — retrodicts as a plain instance of the single defect above, with no separate mechanism needed. One narrow sub-corner is NOT closed by this investigation: an int-ITE or `implies`-antecedent wrapper around the domain-recognition defect's triggering shape sometimes avoids the defect for reasons not traced to source (P9, P12) — see §10.7c's Open note. Full mechanism, retrodiction over every P1–P14 probe (100% match after correction), the decisive probes, the retraction's audit table, and the conservative typed-defer boundary: [§10.7c](docs/reference/alloy6-translation.md#107c-mt-044-mixed-nesting-forbid-mode-trigger-pinned-jar-verified-2026-07-19) and [§10.7d](docs/reference/alloy6-translation.md#107d-mt-044-round-3-shift-semantics-pinned-negate8-forbid-confound-audit-jar-verified-2026-07-19).
**Status:** `approved` (tech lead, no-fork delegation, 2026-07-19; `verified` mt-044 same day — zero open residuals: every named soft spot below was probed shut or amended the Rule, and the one genuinely-jar-unpinned sub-corner (the ITE/`implies` sliver) is carved out of the entry's scope as a standing typed defer per project policy, not a "re-derive later" caveat — mettle never emits a verdict there). ### LEDGER-006 — cardinality `#`
**Rule:** `#e` is a two's-complement `IntExpression` (`cset(e).count()`) at the command bitwidth; it participates in overflow **exactly like arithmetic** — a count exceeding `2^{w-1}−1` **wraps** in allow mode (`#A=8` at bw 4 reads as `−8`) and is an **overflow** in forbid mode (an over-large count excludes the instance under the §11.3 polarity rule). `#` is the only int-producing coercion on a set; there is no implicit set→int elsewhere (no int↔Int coercion — resolution §4.5).

### LEDGER-011 — `univ`/`iden` denotation (the live universe)

### LEDGER-012 — evaluator (REPL) rendering order
**Rule:** A value evaluated at mettle's evaluator prompt renders its tuples in **mettle's own live solve order** — the deterministic `TupleSet` order over the command's universe (sig atoms in declaration/mint order, then integer atoms ascending `-2^(bw-1) … 2^(bw-1)-1`, then string atoms) — **not** the reference GUI console's XML-round-trip order (string atoms first, then integer atoms in the reader's reconstructed `-1..-8, 0..7` sub-order, then sig atoms). The two orders present the **same set**; only the sequence differs, and only for values spanning several atom classes (`univ`, `iden`, `Int`, a union like `3 + A`). ### LEDGER-013 — instance-XML skolem `<types>` columns
**Rule:** In mettle-written instance XML, an **ordinary skolem**'s `<types>` columns are recovered from that skolem's **solver bound** — per column, the least common primitive ancestor of the minting sigs of every atom its upper bound admits, `univ` in the limit — rather than from the declared `Type` the reference reads off the witness's `ExprVar`. The result is always a **sound over-approximation** of the reference's column (the same sig, or a proper ancestor of it), never a narrower claim; every other part of the element (the `<skolem label= ID=>` attributes, the shared ID namespace, the `<tuple>` bodies, the `<types>` element's own shape and position) is the reference's exactly. Fields and **macro** skolems are unaffected — both carry a real declared type in mettle's world and use it directly (via `Type.fold()`).
**Status:** `approved` (tech lead, Option B no-fork delegation, 2026-07-27, at mt-071 review). No fork for the owner: this is a structural consequence of mettle's IR, not a choice between two jar behaviors, and it is invisible to the scorecard (ADR-0002 diffs solve *verdicts*, never instance XML).
**Evidence:** The reference's `writeSkolem` calls `writeExpr(prefix, exprVar, state)`, whose `<types>` tail iterates `exprVar.type().fold()` ([reference/alloy6-instance-xml.md](docs/reference/alloy6-instance-xml.md) §5/§6, bytecode-derived at mt-071). mettle's skolem relations are minted by `als_core::lower`'s `alloc_skolem`, which records a **name, arity and `RelBound`** — the `abstract_upper` over-approximation of the decl's bound (translation-ref §10.6) — and deliberately never a `Type`; there is no declared type to read, and reconstructing one would mean re-deriving the decl's type at write time from data the lowering already discarded. The derived columns are **byte-identical to the jar's** on every skolem this wave probed (`X-05` `$x`/`$y` and `X-05b` `$allSame_x`/`$allSame_y` all yield `<type ID=this/A>`, matching the captures in §6). Where they can differ is a decl whose bound is narrower than the atom pool its columns draw from, in which case mettle names an ancestor sig; the jar's own reader accepts that unchanged — mt-071's differential put **18 mettle-written files through `A4SolutionReader.read`, 18 accepted, 0 rejected** (§11, per-file table in `scratchpad/probe/mt071/NOTES.md`).
**Test:** `crates/als-instance/tests/xml_shape.rs` — `anonymous_command_skolem_naming` and `named_command_skolem_naming` pin both skolem namings together with their `<types>` columns, against the goldens `tests/golden/skolem_run.xml` / `skolem_check.xml` (which transcribe the same shape as the doc's `X-05`/`X-05b` captures). The writer itself is `bound_types`/`least_common_prim`/`atom_sig` in `crates/als-instance/src/xml.rs`.

### LEDGER-014 — temporal trace counting is configuration-relative
**Rule:** mettle's temporal trace enumeration reproduces the jar's *algorithm* verbatim — plain `next()` locks the static configuration to the first solution's (probe P-076-5: the jar never leaves it, verified at `symmetry = 0` and with the freedom in a sig bound and in a field); within a length, duplicates are raw `(states, loop)` pairs; across lengths, de-duplication is by infinite trace; `fork(p≥0)` holds logical states `0..p−1` byte-identical and never moves the trace length; `fork(-1)` restarts the length sweep on a new configuration, with the pinned no-alternate rule (no free static primaries ⇒ the original returned; free but no alternate ⇒ exhausted). **Because both engines count only their own first configuration's traces, exact count parity is not achievable by construction on any command whose configuration space has more than one member** — the two engines count different, individually-correct sets (demonstrated live on `leader.als[3]`, probe P-076-7: the jar's first config is a three-node ring counted to the 10001 cap; mettle's is the empty model, whose whole space is one trace). **Gauge posture:** compare but soften — an agreement is `count_match`; a disagreement on a many-configuration command is the typed `skip_temporal_config`; only a unique-configuration command can raise a temporal `COUNT_MISMATCH`, and there the alarm means what it says.
**Status:** `approved` (tech lead, Option B no-fork delegation, 2026-07-27, at mt-076 review). No fork for the owner: there is no alternative semantics to choose between — the residual is which-first-solution solver discretion of the same family ADR-0002 already accepts for *which instance is shown*; the posture matches the `skip_ho_skolem`/`skip_ordered_abstract` precedent. Alternatives measured, not argued (mt-076 report): comparing anyway leaves 3 permanent false-alarm rows; refusing every many-config command zeroes temporal counting entirely.
**Evidence:** The mt-076 probe wave, cells P-076-0..7 (`scratchpad/probe/mt076/NOTES.md`; [reference/alloy6-temporal.md](docs/reference/alloy6-temporal.md) §(g) "The mt-076 probe wave" + §(i) Correction). Counting nets after: SB-0 `count_match` 53→56, SB-20 77→79, `COUNT_MISMATCH` 0→0 at both settings, `skip_temporal_trace` retired 8→0, `skip_temporal_config` 0/3 (SB-0/SB-20).
**Test:** `crates/als-core/tests/temporal_enum_conformance.rs` (19 probe-cited tests — per-length exhaustion order, config lock, fork prefix-holding byte-checks, `(states, loop)` duplicate unit, across-length dedup, typed budget/cap exhaustion); `leader_als_counts_match_its_real_jar_baseline` in the gauge suite (leader.als's T-26 real jar baseline now a live `count_match`).

### LEDGER-015 — one-state temporal bounds are answered; the jar's constant-folding NPE is not reproduced
**Rule:** mettle answers **every** temporal command at a one-state `steps` bound (`for 1 steps`, `for exactly 1 steps`, `for 1..1 steps`, or a wider scope resolving to `maxtrace == 1`), for `run` and `check` alike, with the ordinary lasso semantics at `k = 1` (a single state looping on itself; `always P` ≡ `eventually P` ≡ `after P` ≡ `once P` ≡ `historically P` ≡ `P`, `X until Y` ≡ `Y`, `before P` ≡ false — probe P-077-3, both polarities). The jar, by contrast, NPE-crashes (`ErrorFatal`, `Translation$Whole.cnf()` on null) on the subset of one-state commands whose translation constant-folds to a boolean — `run` or `check`, probe-bisected (mt-077 cells B1–B6) — and answers the rest. mettle reproduces no part of the crash: where the jar answers, mettle conforms; where the jar crashes, mettle returns the semantically correct verdict the crash withholds.
**Status:** `approved` (**genuine fork, owner-decided Option B, 2026-07-27** — "Do B"). The owner-facing framing and the A/B tradeoff are recorded in the combined review doc's history; the deciding argument: a `check P` is the negated `run {not P}`, and the jar solves `run … for 1 steps` — so the one-state semantics is jar-anchored through the dual, not taken on faith. The mt-077 wave then strengthened B further: the old blanket `check`-at-1 refusal was itself diverging from the jar on the majority (answering) subset — nine one-state `check`s answered cleanly in the wave — so Option B *increases* conformance and confines the deliberate divergence to inputs where the jar produces nothing at all.
**Evidence:** mt-077 probe wave, cells P-077-1..5 + bisect B1–B6 (`scratchpad/probe/mt077/NOTES.md`, predictions-before-runs, verbatim jar output); [reference/alloy6-temporal.md](docs/reference/alloy6-temporal.md) §(c) scope correction (the wave-1 "general to `check` + `maxtrace==1`" and "isolated to `check`" claims are both refuted there, with the T-10a/T-11 probe-log rows annotated). Stage-1 sweep byte-identical before/after (zero corpus incidence); `CounterexampleAtLength.als`'s own header prediction (`"for 1 steps" -> UNSAT`) is reproduced by mettle where the jar crashes. Reported upstream: [AlloyTools#350](https://github.com/AlloyTools/org.alloytools.alloy/issues/350) (owner-filed 2026-07-28).

### LEDGER-016 — multiplicity-expression positional rule (resolve-level reject taxonomy)
Rule: a multiplicity-tagged expression (prefix `set`/`seq` anywhere; prefix `some`/`lone`/`one` only where the grammar's `mult()` converts them — decl bounds and the RHS of `in`; arrow-mults, which propagate up an arrow chain; `exactly`-of minted from a **defined binding** — a defined-field bound `f = e` or a decl written `x = e`) is LEGAL exactly in: sig-field/param/fun-return decl bounds, quantifier decl bounds (all mults **except `exactly`-of, see the amendment**), the RHS of `in`, and function/predicate BODIES; it is REJECTED with "Multiplicity expression not allowed here." in every ordinary expression position (unary/binary operands incl. the LHS of `in`, `#`, join operands, ExprList/ITE/`let` RHS, defined-field bounds with mult), REJECTED with "This cannot be a <set/some/lone>-of expression." in comprehension decl bounds (where only `one`-of is legal, and the bound must additionally be a unary set), and surfaces as a call-resolution failure in call-argument position. Parentheses never strip the flag; the flag does NOT survive macro expansion into a use site.
**Amendment (tech lead, 2026-08-23, at mt-111 implementation):** the original entry's "`exactly` only inside a defined-field bound" understated the producer, and mt-109 §2.5's guess that "This cannot be an exactly-of expression." is source-unreachable is **refuted** — the reachable spelling is a quantifier decl written with `=` instead of `:` (`all u1: User, w1,w2 = u1.profile | …`), which the 88-cell wave never probed (it tested `exactly` only as an expression prefix, where nothing parses). Corrected rule, jar-verified on 9 fresh cells (`scratchpad/probe/mt111/NOTES.md`) and 13 alloy4fun codes: **`exactly`-of is rejected by EVERY quantifier (`all`/`some`/`no`/`one`/`sum`) with the exactly-of message, and by nothing else** — fun/pred parameter lists and sig defined fields take `y = e` happily. Two grammar bounds (both already modeled by mettle's parser): a decl list may not OPEN with `= e`, and a comprehension decl list does not admit `=` at all.
**Amendment 2 (tech lead, 2026-08-23, at mt-117):** the rule's "the RHS of `in`" legal position belongs to the PLAIN operator only. The negated-membership operator forms `not in` / `!in` REJECT a mult on their RHS with the same "Multiplicity expression not allowed here." — jar-verified on cells h01/h04/h05 of the mt-116 wave (`scratchpad/probe/mt116/NOTES.md`), uniform across `some`/`lone` and both spellings, plus real code 040307. The trigger is the operator form alone: negation applied OUTSIDE the comparison (`!(x in (some y))`, cell h03) keeps the plain-`in` acceptance, and the LHS behaves as plain `in`'s LHS (reject — cell h06, already byte-agreeing). Implementation keys on the parser's `negated` flag on the Compare node, so the h03 boundary holds by construction. One honest unprobed extension: arrow-mults on a `not in` RHS ride the same reject path without their own cell (only mult keywords were probed); corpus-scanned zero incidence across all 144 `not in`/`!in` sites.
Status: **approved (tech lead, no-fork delegation)** — verified 2026-08-23; a pure restatement of measured jar behavior, no fork; amendment same day, same basis; amendment 2 same day (mt-117), same basis.
Evidence: mt-109 probe wave, 88 one-cell models against the pinned jar (`scratchpad/probe/mt109/{m,n,p,q}/`, predictions-before-runs in `PREDICTIONS.md`, full write-up `mult-flag.md`): 57 agree / 31 mettle-over-accepts / 0 drop-in. Three counterintuitive pins: fun/pred bodies ACCEPT mult (m18/q01/q02); quantifier bounds accept everything while comprehension bounds reject all but `one`-of (m10/p18 vs n04/p02/p03) — mettle serves both from one `decl_bound_type`, so an implementation needs a caller mode; `in` is asymmetric (RHS consumes n18/p16, LHS rejects m26). Bare unparenthesized forms (`A in set A`) are parse-tier rejects on BOTH sides already — the gap is exclusively bracketed/argument/body positions.
Test: `crates/als-types/tests/resolve_probes.rs` `_mt111` fns (mt-111, 2026-08-23) — the 57 agreeing cells landed first in their own commit against the unmodified resolver, then the 31 flips + the amendment's quantifier-`=` cells with the check.

### LEDGER-017 — polarity-blind translation reuse for shared formula nodes
Rule: a formula reached twice through the SAME source object — a formula-valued `let` binding's uses, or two calls of a ZERO-parameter pred (any parameter, even with the identical argument, severs sharing) — is translated once, at the first visit's ambient polarity and free-variable binding, and every later reach at the same binding reuses that translation verbatim, overflow guards, `in`/`=`/multiplicity guards over `Int[..]`-derived operands, and whole-quantified-formula orientation included; sharing is by node identity never syntactic identity, is severed wherever skolemization rewrites one occurrence differently from another, is polarity-clean at the Expression/Int level (a shared zero-param fun does not diverge), and applies identically in the evaluator.
Mechanism (jar): `FOL2BoolCache` keys on node object identity + a free-variable tuple snapshot and never consults `Environment.negated`; cached values are returned verbatim, never re-guarded; the cache is built post-skolemization; the only Alloy-level producers of shared formula nodes are `visit(ExprLet)` (the env stores the translated object) and `visit(ExprCall)`'s `cacheForConstants` (keyed on the `Func` alone, consulted only when `f.count() == 0`). mettle reproduces this with translation classes over its per-use lowered copies ([ADR-0029](docs/adr/0029-polarity-blind-translation-cache.md)) — mt-056's per-use lowering stands, and a class dissolves when its copies are not structurally identical, which reproduces the post-skolem severing by construction. Deliberately out of scope, recorded in LIMITATIONS: the temporal path (unprobed intersection, zero incidence) and first-visit order under the jar's short-circuit folding on shapes where mettle's conjunct/fold order differs (zero incidence; all probe cells match).
Status: **approved (tech lead, no-fork delegation)** — verified 2026-08-26: pure bug-compatible restatement of measured jar behavior (mettle's polarity-correct answer was the sounder one, but the drop-in North Star decides; the "sounder vs drop-in" question was already settled at the campaign level, no new fork). 16/16 banked predictions hit on the boundary wave; the mechanism cells were pinned at mt-128.
Evidence: `scratchpad/probe/mt128/` x5/x6 (g5/h cells: node-identity sharing, first-visit-wins both directions, same-polarity neutrality) + `scratchpad/probe/mt137/` (j1–j8: the zero-param boundary, the guard family width, skolem severing, fun polarity-cleanliness; `PREDICTIONS.md` banked before running); source contract from `scratchpad/src794/` (`FOL2BoolCache.java:53-225`, `TranslateAlloyToKodkod.java:796-801,976-1025`, `DefCond.java:64-97`, `Skolemizer.java:154-478`).
Test: lands with the mt-137 implementation (`crates/als-core/tests/trans_cache_conformance.rs`, all 18 cells verbatim, both overflow modes, jar-free).
