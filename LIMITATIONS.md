### ~~Int-position `if-then-else` with one integer-literal branch~~ — FIXED (mt-095, 2026-08-20)
The two residual cells of the mt-090 probe round (`e0`/`e6`). **Root cause:** `Lowerer::sort_of` made an int-position `c => A else B` an **int**-ITE whenever *either* branch was int-sorted; the jar's `visit(ExprITE)` dispatches on the **then** branch alone (bytecode `scratchpad/probe/mt095/tak.disasm:1394-1445`) and a bare Alloy NUMBER literal translates to a *set* — `IntConstant.constant(n).toExpression()` is an `IntToExprCast`, which *is* an `Expression`, and `instanceof Expression` is tested before `instanceof IntExpression`. So `(c => plus[n,7] else 0) >= 0` is a **relational** ITE over `Int[·]` casts in the jar (the overflowed cast is empty, §10.7e FACT 2, and `sum ∅ = 0`) where mettle built an int-ITE that kept the accumulated overflow. Fixed by `Lowerer::ite_sort`: the ITE's sort is read off the then branch, with a bare numeral counted as relational. **mt-090's predicted second half — a *dynamic* constant-escape — was REFUTED by the mt-095 wave**: the guard is shed by structure, not by constant-folding (a cast that `toInt` must read with `.sum()` contributes no comparison-level guard; one it UNWRAPS keeps it), and mettle's `lower_int`/`lower_rel` already implemented that faithfully. So the whole fix is at lowering and the encoder and evaluator, which consume the same IR, stay a matched pair by construction. Evidence: translation-ref §10.7g, `scratchpad/probe/mt095/NOTES.md` (**90 jar cells: 28 divergences before, 9 after**, revert-verified, no cell regressed), `crates/als-core/tests/eq_typing_conformance.rs` part D (8 new jar-free tests; the formerly `#[ignore]`d `part_c_mixed_branch_ite_is_relational_in_the_jar` now passes). Zero corpus rows move — the full stage-1 sweep is byte-identical across the change.

**Residual divergences — all latent, zero corpus incidence. The four families mt-095 disclosed were triaged at mt-096 and ALL FOUR ARE PINNED, each with a measured blocker rather than a guess; the set-former guard corner below was measured in the same wave and is pinned too (translation-ref §10.7h).**
- **Adversarially long flat operator chains are rejected, not parsed (mt-021, ADR-0022) — a deliberate better-than-reference divergence.** The parser bounds root-to-leaf AST **path depth** at `MAX_AST_PATH = 768` and fails with the same typed `ParseError::TooDeep` the nesting guard uses. Without it a plain `.als` file aborted the process (`SIGABRT`): `mettle parse` at ~58k chain terms, `mettle parse --ast` at ~52k, and **`mettle check`/`exec` at ~3.7k** — the parser's existing `MAX_EXPR_DEPTH` counts *nesting*, and a flat chain has nesting depth 1, so it sailed through. **The reference is not safe here either** — the jar throws a raw `java.lang.StackOverflowError` at 5,000 terms — so there is no conforming behaviour to preserve, only a crash to replace with a diagnostic (exactly the `MAX_EXPR_DEPTH` precedent). Real input is nowhere near: the bound is **4.8×** below the worst measured crash (`A.r.r.r…`, 3,687), **6.8×** above the longest chain in the 150,891-code alloy4fun corpus (113), and **96×** above the longest in the vendored corpus (8). The alloy4fun resolve gauge is **byte-identical across the change over all 150,891 codes** (102,284 accept / 48,607 reject / 0 panic, unchanged), so it rejects no real model. **Residual:** an `Ast` built programmatically through the `als-syntax` API never passes the parser, so `print`/`dump` stay unbounded there in release builds — documented as `print::MAX_SAFE_PRINT_PATH`; closing it needs ADR-0022's option (a), the iterative printer rewrite, evaluated and rejected as neither contained nor sufficient.

- **`int[·]` in an ITE branch — PINNED (mt-096)** (probe i8). Needs resolver-side surface information mettle deliberately does not carry. Alloy's resolver re-wraps a surface `int[e]` as `Int[int[e]]` (`ExprUnary.int->Int` over `ExprUnary.Int->int`, visible in `q1_ast.txt`), making the branch a set, while `#e` in the identical position is *not* re-wrapped. Both carry Alloy type `{Int}`, so its type system does not distinguish them — an inconsistency inside Alloy's own `ExprUnary` resolution that mettle has no wrapper to read. Narrow: probe m1 (`int[plus[n,7]]` as the then branch) agrees.
- **`#` applies a shrouded cast's guard where `sum` does not — PINNED (mt-096)** (probes i13, k8, and mt-096's f3r4/f4r4/f6r4/f7r4/f8r4). mt-096 measured the whole former × reader matrix: `#` behaves like the set-level readers (it keeps the guard through an intersection, difference, if-then-else or join) and sheds only where they shed, so closing it is **entangled with the unpinned union corner below** and cannot be done independently. `#` over an ITE-shrouded cast is jar UNSAT while the `sum` reading of the same set is SAT — but `#` over a *union*-shrouded cast (k9) does not guard, so it is not simply "`count` propagates". Mechanism not chased.
- **`toInt`'s double-unwrap discards `#` under an int reader — PINNED (mt-096)** (probes k10/k12, decisively n6/n7 in `q6_carddiscard.als`). When the operand of `#` is itself an `Int[·]` cast **and the result is read by `cint`** — `<`, `>`, `<=`, `>=`, or an int operand position — the jar's `toInt` first arm fires (`ExprToIntCast` over `IntToExprCast → intExpr()`) and it yields the operand's **raw integer**, throwing the cardinality away. Under a **set** reader (`=`, `in`) no `cint` is called and `#` stays an ordinary cardinality. Pinned with **no overflow anywhere**, so it is structural rather than a guard artifact: `plus[3,4]` is the one-element set `{7}`, and `#(plus[3,4]) = 1` is SAT on both sides while **`#(plus[3,4]) >= 7` is jar SAT and mettle UNSAT** (the jar reads 7, mettle reads 1). Negative space holds on both sides: `#Node >= 3` at `exactly 3 Node` and `#(plus[3,4] + plus[1,1]) >= 2` are SAT — a real relation, and a union that is not a bare cast, stay real cardinalities. k12 is the same family on the `int[·]` reader. Separately, **k11 (`#(plus[n,7]) = 0`, jar UNSAT) is a DIFFERENT corner**: it is a set comparison, so `#` really is a cardinality — the UNSAT is the cast's guard firing through the `Card` operand, which §10.7e already lists as out of scope and which now has jar cells attached. **mt-096 measured the fix and it is not the one-line peephole it looks like:** adding the jar's double-unwrap to `lower_int`'s `Card`/`IntOf` arms fixes n6/n7 but *breaks* n1/n2, because mettle routes `#X = 1` through `lower_int` too (both sides are `Sort::Int`) where the jar does a **set** comparison there — its `EQUALS` int-compares only when both operands are literally `IntToExprCast`, and `#X` is an `ExprToIntCast`. Net divergences stayed at 2; the peephole only moved them. Closing this needs the int-compare gate re-keyed on the jar's literal-cast test first (§10.7e FACT 1 / §2.2 routing), which is its own bead.
- **`sort_of` does not follow a `let` to an int-valued RHS — PINNED (mt-096)** (probe i23; its numeral twin i22 agrees, a clean minimal pair). The blocker is scoping, not the mt-056 machinery: `ite_sort` runs on the *then branch* before lowering descends into it, so the `let`'s binder is not yet on `self.binders` and the bound name still reads as relational. Closing it needs either a local substitution env threaded through `ite_sort` (the jar's `visit(ExprLet)` puts `visitThis(expr)` in `env` and returns `visitThis(sub)`, so faithfulness wants exactly that) or the sort computed after binder push — a design choice, not a chunk-tail edit.
- **The set-former guard corner (was "FACT 3 is too strong") — MEASURED AND PINNED at mt-096, translation-ref §10.7h.** mt-095 saw a union-nested cast shed the guard (k4/k16, jar SAT / mettle UNSAT) and LEDGER-010 was amended to say *any* set former sheds. mt-096 measured that across a former × reader matrix (75 cells) and the amendment is **too broad**: the jar keeps the guard through an intersection, a difference, an if-then-else, a join, an override and a product, and mettle already matched it on 26 of the 36 matrix cells — implementing the amended wording literally would have **regressed 12 agreeing cells**. Only the union (and the comprehension, which mettle already sheds by refusing to enter formula positions) sheds, and even that is not a rule: a union of **two** capable casts guards (u11/v3), the identical union shape **without** a quantifier guards (t4c — mt-051's T1/T4, re-probed and re-confirmed), and a sibling that cannot actually overflow sheds (v1). Three candidate rules were implemented or evaluated and each was refuted by a cell, so mettle keeps descending through unions — the **conservative** direction: it can turn a jar SAT into a mettle UNSAT, never a jar UNSAT into a mettle SAT. Pinned by the `#[ignore]`d `part_e_union_sheds_under_a_quantifier_in_the_jar` (12 jar cells); six passing part-E tests hold the measured negative space. **LEDGER-010's layer (2) should revert to its pre-mt-095 "unions included" wording** with §10.7h cited as the exception list.

### ~~Shared subformula translated at two polarities (`FOL2BoolCache`)~~ — PROBED, no divergence (mt-095, 2026-08-20)
mt-090's "also surfaced and unprobed". The mechanism is real and now demonstrated with a minimal pair, but **mettle agrees on all 16 cells in both overflow modes**, so there is nothing latent here. Two spellings of one formula give opposite jar verdicts, twice: `run { (#Node < 0) or (not (#Node < 0)) }` at `exactly 8 Node` is **UNSAT** while `run { let p = (#Node < 0) | p or (not p) }` is **SAT**; `(#Node<0) => (no Node) else (no Node)` is **UNSAT** while its hand-written conjunction is **SAT**. Written out, each occurrence is its own Kodkod node translated at its own polarity (positive `cmp ∧ ¬of`, negated `cmp ∨ of`), so LEM is false — which is *correct* `noOverflow` semantics, an overflowing comparison being false at both polarities is exactly how Alloy prunes overflow from both directions. With a `let`, or via `visit(ExprITE)`'s single `cform(x.cond)`, one node appears both bare and under a `NotFormula` and `FOL2BoolCache` — keyed on (node, free-variable bindings), not on `Environment.negated` — hands back the first visit's translation. mettle matches because it shares the same way: its formula-ITE lowering translates the condition once at the ITE's own polarity, and mt-056's eager formula-`let` lowering translates a `let` RHS once at the binding site. The sub-corner mt-090 called untested — the shared node under a quantifier, so the cache key carries a free-variable binding — is covered by cells 10–13 and agrees too. Evidence: translation-ref §10.7g, `scratchpad/probe/mt095/{q3_g5cache.als,q3_g5cache_jar.txt,NOTES.md}`.

### Rung-6 temporal solving (mt-067) — bounded lasso only, deliberately
The temporal driver (`crates/als-core/src/temporal_solve.rs`, [ADR-0015](docs/adr/0015-rung6-temporal-architecture.md) §3) sweeps a temporal command's resolved `steps` range ascending and returns the first (minimal) SAT as a `k`-state lasso trace, exactly as `TemporalPardinusSolver.solve` does ([reference/alloy6-temporal.md](docs/reference/alloy6-temporal.md) §(c)). The honest edges:

- **UNSAT means "no instance/counterexample within the `steps` bound", never "the assertion holds".** Raising the bound can flip it (probe T-10b). `mettle exec` says so in the verdict line (`VALID (no counterexample within 10 steps)`).
- **Unbounded (`for 1.. steps`) model checking is out of scope, matching the jar out of the box.** The reference's default bounded engine refuses it with `ErrorAPI("Bounded engines do not support complete model checking.")` before any solving (probe T-08b, reconfirmed by two `trash.als` corpus commands); reaching the unbounded path needs the external `electrod.elo` solver, whose own semantics the contract could not vouch for (T-27 reports an unexplained UNSAT with a "possibly unsound" jar warning). mettle raises the jar's exact message as a typed defer.
- ~~**`check … for 1 steps` is a typed defer naming a pinned jar bug, not a verdict.**~~ **DECIDED AND IMPLEMENTED (mt-077, [LEDGER-015](SEMANTICS_LEDGER.md#ledger-015--one-state-temporal-bounds-are-answered-the-jars-constant-folding-npe-is-not-reproduced), owner-decided Option B, 2026-07-27): mettle answers every one-state-bound temporal command.** The honest edge that remains is the reference's, not mettle's: the jar NPE-crashes (`ErrorFatal`, `Translation$Whole.cnf()` on null) on the subset of one-state commands — `run` *or* `check`, the mt-077 probe wave refuted wave 1's "isolated to `check`" reading — whose translation constant-folds to a boolean, and answers the rest. Where the jar answers, mettle conforms (nine one-state `check` cells verified, P-077-1/2/4/5; the semantics is jar-anchored through the negated-`run` dual). Where the jar crashes, mettle deliberately diverges by returning the semantically correct verdict the crash withholds — a divergence invisible to the scorecard (the jar produces no verdict to compare) and validated against the dual plus `CounterexampleAtLength.als`'s own header prediction. Zero corpus incidence; stage-1 sweep byte-identical across the change. The crash is reported upstream as [AlloyTools#350](https://github.com/AlloyTools/org.alloytools.alloy/issues/350) (2026-07-28).
- ~~**Trace enumeration / counting is deferred (ADR-0015 consequence 4).**~~ **IMPLEMENTED (mt-076).** `als_core::temporal_enum::TraceEnumerator` implements the jar's `next()`/`fork(p)` family against the mt-076 probe wave ([reference/alloy6-temporal.md](docs/reference/alloy6-temporal.md) §(g), `scratchpad/probe/mt076/NOTES.md`); `skip_temporal_trace` is retired and temporal SAT commands are counted and compared like any other. **The honest edge, and it is a real one: a temporal count is configuration-relative.** Probe P-076-5 pinned that the jar's plain `next()` never leaves the static configuration its first solve landed on — proven at `symmetry = 0`, and with the static freedom in a sig bound and in a field — so the jar's banked count is "the traces of *sat4j's* first configuration" and mettle's is "the traces of *mettle's*". On a command whose configuration space has more than one member the two engines count different sets, and exact parity is **not achievable by construction**. It is not hypothetical: on `leader.als[3]` the jar's first solution is a full three-node ring (counting to the 10001 cap) while mettle's is the empty model, whose whole space genuinely is one trace (probe P-076-7). mettle reproduces the algorithm verbatim (config-lock at its own first solution, across-length de-duplication by infinite trace, raw `(states, loop)` counting within a length). **The gauge therefore compares but does not cry wolf:** an agreement is a `count_match`; a *disagreement* on a command with more than one configuration is bucketed `skip_temporal_config`, not `COUNT_MISMATCH` — only a unique-configuration command can raise a temporal count alarm, and there the alarm means what it says.
- **Trace rendering matches the reference's *shape*, not its line syntax (mt-068).** `mettle exec` prints a SAT temporal command as the reference's `A4Solution.toString(-1)` does (contract §(f), source-pinned and probe-captured): a `---Trace---` header, one `------State N-------` block per state with `(loop)` on the back-loop target, and every relation — rigid content included — re-emitted in full in each block. **Inside** a block the lines are mettle's own established instance rendering (`  this/S = {…}`, `  this/S.f = {…}`, skolems by relation name) rather than the reference's `label=…` / `label<:field=…` / `skolem …=…` syntax, and tuple order is mettle's live solve order. Both are the [LEDGER-012](SEMANTICS_LEDGER.md#ledger-012--evaluator-repl-rendering-order) posture — identical sets, different spelling, invisible to the scorecard (ADR-0002 never diffs instance text), and identical to what the static path has printed since mt-036.
- **Per-state symmetry breaking is relation-major, the jar's is state-major.** The pinned rule (`SymmetryBreaker.java:207-259`) applies the lex-leader predicate independently at every state and excludes skolem relations unconditionally in temporal mode. mettle gets the first for free — its unrolled per-state relation copies are ordinary relations over a rigid atom universe, so the partition is computed once and each copy gets a static relation's treatment — and gates the second explicitly. The remaining difference is the *bit order* within the lex chain: mettle groups a relation's `k` state copies adjacently, the jar groups a state's relations adjacently. Any fixed bit order is a sound lex-leader and the predicate is Tseitin-only, so this is verdict-neutral by construction; it can only differ in which isomorphic representative survives, which matters solely to enumeration — which is deferred anyway. A copy's state index is written in decimal without padding, so within one relation the copies sort decimally only up to `k = 10` and lexicographically beyond (`leader.als`'s `15 steps`); pinned by test, deliberate (padding would make a relation's *name* depend on `k`).
- ~~**`for exactly N..M steps` is a confirmed wrong-verdict-class divergence, open.**~~ **FIXED (mt-067 follow-up, tech-lead approved).** Probed at mt-069 (`scratchpad/probe/mt069/NOTES.md`, cells L6/L6b): the jar's parser silently collapses `exactly N..M` to `N..N` at `Command`-construction time, discarding the written upper bound entirely (confirmed via `Command.toString()` and via `getMinTrace()`/`getMaxTrace()` on a real temporal solve). mettle's `als_types::resolve::members::steps_scope` kept the full written range `[N,M]` regardless of the `exactly` flag, so it searched a *wider* steps range than the jar — a model SAT only at length 4 or 5 but not 3 would have flipped mettle's verdict relative to the jar's `[3,3]`-bounded UNSAT. It now collapses to `[N,N]`, so the search range matches, not just the rendering. Regression tests (jar-free, citing L6/L6b) in `crates/als-core/tests/temporal_solve_conformance.rs`: `exactly_discards_a_written_steps_range_end` (the resolved range plus the no-`exactly` control) and `exactly_collapses_the_search_range_not_just_its_rendering` (a P-C6 prime chain satisfiable only at length 3 under `exactly 2..4 steps` → UNSAT-within-bound; SAT at 3 under the plain `2..4` control). Zero corpus incidence either way. **Residual, still unprobed and deliberately unchanged:** `for exactly N.. steps` (`exactly` on an *open* range) — L6/L6b covered only the bounded shape, so `exactly` stays ignored there and that syntax behaves exactly as before (`1..` accepted then refused by the bounded engine; any other start rejected). Not guessed at; it needs its own probe cell.
- **A macro whose body contains a temporal operator used to be invisible to mettle's `isTemporalModel` discriminator — divergence found by mt-069 (STOP-THE-LINE), now FIXED in a tech-lead-approved mt-065 follow-up.** Probed (`scratchpad/probe/mt069/NOTES.md`, cells K4a/K4b): the jar expands a top-level `let` macro's body *before* `CompUtil.isTemporalModel`'s scan runs, so a macro used from a fact or a command body, whose own body has a temporal operator (e.g. `let m = always some A`), makes the command temporal (`isTemporalModel = true`, confirmed both ways). mettle's `als_types::temporal` walked the **surface** AST, where a used macro reference is `ExprKind::Name(_)` — a leaf, by the same non-descent rule that correctly excludes a called pred/fun's body (§(k) item 1, probe K1) — so it misclassified such a command as static, rejecting a `steps` scope the jar accepts and solves with real temporal semantics (verified against the built binary). The scan now follows a macro use into its body via the recorded `MacroChoice` (the same replay seam `als_core::lower` uses, so name resolution is read rather than re-derived), descends nested macro uses through the call site's nested choice table, and walks each macro body at most once per scan — which doubles as the cycle guard. A called pred/fun body is still **not** descended (K1 unchanged). Zero corpus incidence either way (grepped both corpora for a temporal-operator-bearing top-level macro; none found), so no banked verdicts moved. Regression tests, jar-free and citing K4a/K4b, in `crates/als-core/tests/temporal_conformance.rs`. **Residual, unprobed:** an *unused* macro whose body holds a temporal operator is treated as **not** temporal — the natural consequence of it never entering `globalFacts` or the command body, but K4a/K4b pinned only the *used* shapes, so it stays an assumption (recorded in [SEMANTICS_LEDGER.md](SEMANTICS_LEDGER.md)).

### Rung-5 evaluator REPL (mt-062) — honest edges
`mettle exec --repl` / `--eval <EXPR>` evaluates expressions against one solved command's instance, implemented from the jar-pinned contract in [docs/reference/alloy6-evaluator.md](docs/reference/alloy6-evaluator.md). Rendering shapes match the reference exactly (`{a->b, …}`, `{}`, `true`/`false`, `{7}` for `plus[3,4]`, `{3}` for a bare `3`, a bare numeral only for `#e` / a `sum` quantifier / a shift, string atoms with their quotes); the edges that do **not** match, all deliberate:

- **Tuple order is mettle's live solve order, not the reference console's ([LEDGER-012](SEMANTICS_LEDGER.md#ledger-012--evaluator-repl-rendering-order)).** For values spanning several atom classes — `univ`, `iden`, `Int`, a union like `3 + A` — mettle renders sig atoms (declaration order), then integer atoms ascending, then string atoms; the reference GUI console renders string atoms first, then integers in its XML reader's reconstructed `-1..-8, 0..7` sub-order, then sig atoms. **The sets are identical**; only the sequence differs. Matching the console byte-for-byte would mean replicating its XML serialize-then-reparse round-trip purely for the reordering side effect — the contract's own §5 recommends against it, and the scorecard never diffs instance tuple order. (The jar renders mettle's order when the same expression is evaluated against its *live* solved object; both orders are pinned jar behavior, from two different jar code paths.)
- ~~**The evaluator prints atom labels it cannot read back.**~~ **FIXED (mt-098, 2026-08-20.)** An atom of a sig declared in an *opened* module prints under its module-qualified label (`so/Ord$0`, `sr/SeqIdx$0`) and is now legal input again, so **every atom the instance prints round-trips** (verified over whole universes: 30/30 and 20/20). The jar's rule, newly pinned because the contract was silent on it (evaluator contract §1, probes E-50–E-58): an atom's label is registered **verbatim** by `addGlobal` and resolves by **exact match on the whole string**, never through module-qualified lookup — which is why two aliases of one module give distinct atoms, why `enum`'s implicitly-opened un-aliased `ordering/Ord$0` coexists with them, and why the *sig's* own qualified name (`so/Ord`) is **not** reachable in the evaluator at all. The break was in `resolve_name`: every env lookup was gated on a single-segment name, so a two-segment name fell through to the `$`-leniency, which returned `univ` **without recording a choice** and left lowering with nothing to replay. Fixed by `Cx::env_get_qualified`, gated on evaluator-fragment input and matching only names the instance actually registered; the alloy4fun resolve gauge is byte-identical over all 150,891 codes, proving the gate holds. Look-alikes (`so/Ord$1`, `zz/Ord$0`, `A$9`, `so/Nope$0`) are rejected as the jar rejects them, with mettle's own message text.
- ~~**A bare numeral literal renders as a bare numeral, where the jar renders a singleton.**~~ **FIXED (mt-099, 2026-08-21.)** Probing around mt-098's one-cell finding showed the divergence was broader and ran in *both* directions, and that it is one clean rule (evaluator contract §3, probes E-59–E-79; 44/44 cells now agree on the banked fixture). The jar renders bare only what `A4Solution.eval` receives as a Kodkod `IntExpression`; the int **type** is not the discriminator — every cell measured carries Alloy type `{Int}` with `is_int` set, the `{n}` ones included. So a numeral literal (`3`, `-3`, and out-of-range `8` → `{-8}`, which wraps silently), `int[e]`/`sum e`/`sum[e]`, and every `integer/*` call render `{n}`; only `#e`, a `sum x: d | e` quantifier, and a shift render bare; and `Int[e]`, `let`, parentheses/`{e}` and an `if-then-else`'s then branch are transparent, so `Int[#A]` and `let x = #A | x` render bare `1` where mettle used to print `{1}`. The mechanism is §0 step 8's `parseOneExpression_fromString`, which re-resolves the parsed body against its own type — re-wrapping a `CAST2INT` root as `Int[int[e]]` and stripping a user-written `Int[·]`. Fixed by `Lowerer::fragment_sort`, selected via `FragmentRoot::Evaluator`; `Lowerer::sort_of` (the solve path's classifier, asking the different in-expression-coercion question) is untouched, and the full stage-1 solve sweep is byte-identical. The round-trip got *simpler*: every atom the evaluator prints, int atoms included, now re-enters as `{atom}`.
- **Only sig atoms are registered as names.** The reference registers every atom of the instance as a global; mettle registers the sig atoms (`A$0`, `mesh/Vertex$1`). An integer atom is named `-3` and a string atom `"hi"` — neither lexes as an identifier, so neither was ever reachable by name; they are reached as arithmetic and as string literals respectively, exactly as in the reference. Also registered, per the contract: every skolem name the solve minted (`$foo_x`).
- **A name is bound for every sig atom in the universe, including ones no sig currently holds.** The reference's instance display renames sig-unclaimed atoms (`unused0`); mettle keeps the minting sig's own name, so `A$2` names that atom even in an instance where `A = {A$0}` (and evaluates to `{A$2}` — a name for an atom, not a claim about any sig's population). Unprobed corner: which label the reference's evaluator accepts for such an atom was not pinned by mt-061.
- **Error text is mettle's, except where the message states an evaluator rule.** Parse, unknown-name and type errors render as mettle's caret diagnostics against a synthetic `<repl>` source rather than mimicking the reference's generated-parser text (its 38-token "possible tokens" list is an artifact of its parser generator, not a fact about Alloy). Two messages *are* the reference's, because they state a rule rather than a syntax fact: `Higher-order quantification is not allowed in the evaluator.` and `String literal "…" does not exist in this instance.`
- **An under-applied pred/fun gets mettle's generic lowering message.** `isEmpty` typed with no arguments (contract E-22) is rejected, but with "name without a recorded resolution" rather than the reference's parameter-list explanation — mettle's resolver deliberately leans accept on a bare name that matches an arity>0 callable (the `seen_dollar`/meta leniency path above), so the rejection lands in the lowerer, which has no parameter list to quote. Correct verdict, worse message.
- **Deliberately out of scope for this bead** (each is later work, not a defect): instance enumeration / "next instance" navigation from the prompt; readline-grade line editing and history (the loop is a hand-rolled `read_line`, with no dependency taken for it); Sterling/`serve` integration. (Temporal **state indices** were this list's fourth entry and shipped at mt-068 — see below.)
- **A string literal the solved command never referenced cannot be evaluated** — it has no atom in that command's universe, so `"hello"` against a model that never mentions it is rejected with the reference's own wording. This is the reference's behavior too, not a mettle gap.

### Rung-6 per-state evaluation (mt-068) — honest edges
A temporal command's `--repl`/`--eval` evaluates against the solved lasso at a current state (`--state N`, `:state N` at the prompt), with the pinned index rule: `N >= k` wraps through the loop, `N < 0` clamps to 0, neither is ever an error (contract §(h), probes T-22/T-23/T-25). All 11 temporal operators and `'` are legal input, evaluated relative to that state over the *solved* loop target (T-24) by the same LTL-on-lasso machinery the solve used. The edges:
- **A state index is a *time* index on the infinite trace** (probe **P-068-1**, this bead's own — the wave-2 fixture loops on its last state, so the question was open). `N ∈ [0,k)` is the first pass; `N >= k` is a later pass through the loop, whose present-tense values are the wrapped state's and whose future is pass-invariant, but whose **past** contains the earlier passes: on a trace looping back to state 0, `once some A` is false at state 0 and true at state 2. mettle implements the jar exactly here (the pass is capped at the fragment's past-nesting depth, which is exact — `d`-deep past values agree from pass `d` on — and bounds the work for an absurd index). The reference *GUI* never reaches these indices (its `<`/`>` arrows normalize into `[0,k)` first); the API and mettle's CLI do.
- **A *static* command's evaluator still defers temporal operators**, typed (`temporal operators are parsed but not yet solvable`) with a caret. **Now pinned (mt-069, probe M068):** the jar does **not** throw here — it evaluates over its degenerate one-state trace exactly as predicted (`traceLength=1, loopState=0`, the same length-1 self-loop machinery behind the "`isTemporal()==true` on a static solve" quirk); e.g. `once some A` evaluates fine at any state index. mettle's refusal is therefore a **conservative capability gap, not a wrong answer** (it declines where the jar would answer correctly) — not a conformance divergence, just an unimplemented case for a later REPL bead (the fix is reusing `eliminate_fragment_at_state` against the static solve's length-1 self-loop trace; the dispatch just needs to stop short-circuiting to the typed refusal first).
- **No trace enumeration is offered or implied.** The prompt's only trace affordance is `:state`, the client-side equivalent of the GUI's `<`/`>` arrows; the four enumeration buttons (New Config / New Trace / New Init / New Fork, contract §(g)) are classified but unimplemented, and nothing in the CLI's surface suggests otherwise.
- **`mettle exec` applies no solve budgets, deliberately** — the reference runs a command until it answers, and `exec` is the drop-in surface, so a wide `steps` range on a big model can genuinely grind (`--conflicts` / `--encode-budget` are the opt-ins; the conformance gauge owns budgeted sweeps).

### Rung-5 instance-XML export (mt-071) — cosmetic divergences only

`mettle exec <file.als> --xml <PATH>` writes one solved command as Alloy instance XML, implemented from the jar-pinned schema in [docs/reference/alloy6-instance-xml.md](docs/reference/alloy6-instance-xml.md). The **structure** is the reference writer's exactly — element order, the lazy touch-order ID scheme, interleaved fields, the `macros` mechanism (`m<i>` skolems *and* the past-depth extra-instance blocks), `<types>`/`<tuple>` gating, escaping, `looplength` — and the jar's own `A4SolutionReader.read` accepted every file mt-071 fed it (18/18, §11). Three things are nevertheless **not** byte-identical to what the jar would write for the same model. None is scorecard-visible (ADR-0002 diffs verdicts, never instance XML), and none affects a reader:

- **`m<i>` index assignment.** The *set* of macro skolems matches the jar's rule exactly (every reachable zero-arg relational `fun`, `util/integer` excluded by module name), but the index each one gets follows mettle's `FuncId` order — declaration order across modules, root module first — where the jar follows `getAllReachableModules()` order. Same entries, possibly permuted `m0`/`m1`/…; the labels (`$this/Best`, `$ordering/first`) disambiguate them regardless.
- **`<source filename=>` spellings.** mettle writes the model path **as given on the command line** and names embedded-stdlib modules `<stdlib>/util/integer.als`; the jar writes an absolute path and `/$alloy4$/models/util/integer.als`. The *content* is escaped identically, and mettle reproduces §9's surprise (the `util/integer` entry is always present even without an explicit `open`).
- **Skolem `<types>` columns** are derived from the solver bound rather than a declared type — filed as [LEDGER-013](SEMANTICS_LEDGER.md#ledger-013--instance-xml-skolem-types-columns), `approved`, with the reasoning and the soundness argument there.

Not new here, but visible in any exported file: **atom labels for a non-exact subsig** differ from the jar's (mettle mints subsig atoms out of the parent's pool, so `sig B extends A` yields `A$2` where the jar yields `B$0`). That is mettle's scope phase, pre-existing since mt-029 and the same [LEDGER-012](SEMANTICS_LEDGER.md#ledger-012--evaluator-repl-rendering-order) "shapes exact, names and order are mettle's" posture — the XML writer just surfaces it.

Deliberately out of scope for this bead: `writeMetamodel` / `metamodel="yes"` (§10 — a separate jar entry point that never co-occurs with a solved instance), and the Sterling `backloop` dialect adapter (mt-072's, per ADR-0016 Decision 2 — the `--xml` path stays jar-exact).

### Rung-5 `mettle serve` (mt-072 backend, mt-075 frontend, mt-076 temporal enumeration)

`mettle serve <file.als> [--command <sel>] [--port N]` solves **one** command and answers the pinned Sterling provider protocol ([docs/reference/sterling.md](docs/reference/sterling.md) §2) on `127.0.0.1` until Ctrl-C: `data` is mt-071's XML byte for byte, `eval` is the `--repl` evaluator's own answer, `click next` is `als_core`'s instance enumerator, `meta`/`ping` are the remaining two verbs. None of this is scorecard-visible — the reference jar ships no Sterling at all, so every choice here is a mettle design decision and never a conformance bug (ADR-0016 Decision 2). What it does **not** do yet:

- **The frontend has both views (mt-075), and neither is customizable.** The served page is mettle's own app: a **graph view** (deterministic hand-rolled layered layout — a node per atom coloured by its sig, a labelled edge per tuple, back edges and self-loops drawn as such, wheel-zoom/drag-pan/double-click-to-fit), a **table view** (a card per signature, relation and skolem), the trace stepper (one chip per state, the loop target marked, stepping client-side), the evaluator pane (`:state N` included), and whatever action buttons the provider currently offers. Hovering an atom, a tuple or a legend key dims everything else; clicking pins that focus. What is **not** there: projection over sigs, any hand-placement or persistence of layout (the drawing is a pure function of the instance, so reloading gives the same one), user themes beyond following the system's light/dark preference, and per-relation show/hide beyond the builtin/`private` toggle the reference visualizer also has. Edge labels are dealt into five lanes using **estimated** character widths — the layout has to stay a pure function, so it never measures rendered text — which spreads a dense bundle without guaranteeing that two labels never touch.
- **Temporal traces enumerate live (mt-076), with one conservatively-chosen unprobed corner.** All five temporal click verbs answer (`next` ≡ `next-trace`, `next-config`, `new-init` = fork(0), `new-fork` = fork at the displayed state), with jar-parity semantics pinned by the P-076 probe wave — including the configuration lock ([LEDGER-014](SEMANTICS_LEDGER.md): temporal counts/enumeration are configuration-relative by construction). The one corner the probes did not pin: `next` *after* a fork stays inside the fork's trace length (documented in code and [reference/alloy6-temporal.md](docs/reference/alloy6-temporal.md) §(g)); budget/capacity exhaustion mid-enumeration is a typed stop, never a repeated or wrong trace. `exec --repl` still has no enumeration surface (symmetric with static commands, which have none either).
- **An external Sterling loses a trace's loop point.** mettle serves the jar dialect (`looplength`); the `sterling-ts` parser reads `backloop`/`loop` and never `looplength` (§2.4). mettle's own frontend reads the jar dialect, so this only affects best-effort interop with an upstream Sterling build — and the `backloop` adapter stays unwritten until someone needs it (ADR-0016 Resolution 1 demoted it from a gate).
- **A stale `datumId` is refused, not answered.** Forge, the only reference provider, warns to its own log and answers about its *current* instance regardless ("reporting back inaccurate data!", §5). mettle answers with a sentence naming the datum it is now on instead: an answer about a different instance is a wrong answer.
- **`serve` takes almost no solve knobs.** `--allow-overflow`, `--conflicts` and `--encode-budget` are `exec` options; `serve` always solves at those defaults. `--solver` is the one exception (mt-089), because which backend answered is not a knob a visualization can leave unstated.
- **One session, one command, no shutdown verb.** Several browser tabs share one solved session behind a mutex (so an enumeration cannot interleave), a file with several commands needs `--command`, and the server stops on Ctrl-C — the protocol has no shutdown message and mettle does not invent one.

### The optional `--solver cadical` backend (mt-089, ADR-0019) — off in every shipped artifact, and not byte-pinned across platforms

`mettle exec`/`mettle serve` take `--solver <name>`. The default, `mettle`, is the hand-rolled CDCL this project owns, and it is the **only** backend under the determinism contract, the only one the conformance scorecard is measured on, and the only one the counting nets and sweep baselines are ever computed with ([ADR-0019](docs/adr/0019-optional-cadical-backend.md) §2). `cadical` selects a far stronger search (CaDiCaL 1.9.5 via the MIT `cadical` crate) and is the honest trade the owner accepted: more of the hard tail becomes answerable, and these guarantees are given up in exchange.

- **Not in the binaries we ship.** The cargo feature that compiles it is **off** in the release artifacts, the container image and the nix package, so on an installed `mettle` the name `cadical` is refused with "not in this build" and the list of what is available — never a silent fall back to the default. It is a source-build opt-in: `cargo build --release -p mettle --features cadical`. The reason is packaging: the backend compiles ~100 vendored C++ files, and the four release targets, the `rust:1.97.0-slim` builder and the sandboxed nix derivation are all built on the premise that nothing in this workspace needs a C++ toolchain (ADR-0016). **We have not yet demonstrated that all four targets can build it**, so we do not ship as if we had. `.github/workflows/backend-determinism.yml` is the experiment that would settle it, and it runs on the next `v*` tag.
- **Deterministic per build, not across platforms.** A fixed CaDiCaL build on a fixed machine answers identically every run, and mettle adds nothing non-deterministic around it (no wall-clock knob is exposed on the CLI path — the instrument's `--wall` deadline is dev-side only). But CaDiCaL's restart policy compares floating-point EMAs of clause glue, so the same sources compiled for a different architecture can legitimately make different search choices and report a **different instance** (never a different verdict — see below). `.cargo/config.toml` pins `-ffp-contract=off` for the vendored C++, which withdraws the FMA-contraction licence that is the one known cause of that; whether anything else remains is measured by the cross-target battery, **not yet run** (it needs a real multi-target CI run). Until it has: treat `--solver cadical` output as reproducible on your machine and unpinned between machines.
- **Verdicts, however, are backend-independent — and that is checked.** SAT/UNSAT is a property of the encoding, not of the solver, so any verdict difference between backends on the same CNF is a bug. `backend-instrument --cross` (dev-side, `--features cadical-instrument`) encodes each row once and decides it with **both** backends, failing the run on any difference. That check needs no jar and no baseline, and it is what caught the mt-090 latent wrong verdict.
- **`--conflicts` narrows in meaning.** The budget binds on both backends and means the same thing — at most N conflicts per solve, and the solver stays usable afterwards — but CaDiCaL exposes **no conflict counter** anywhere reachable (the C++ `Stats` struct is private to its `Internal` class, and the C API's only statistics entry point prints rather than returns), so what a solve *spent* is unobservable under it. Three consequences, none silent: `UNKNOWN (conflict budget exhausted)` cannot be accompanied by a spend figure; the cumulative enumeration-effort budget (the counting net's `--enum-budget`, which is charged from conflicts + decisions + propagation visits) is refused outright on a backend without counters rather than being charged zero; and `--decisions`-style budgets do not exist on either backend.
- **Counting stays own-CDCL.** Enumeration under `cadical` is still **exact** — every distinct instance appears once and the sequence ends at a true UNSAT, which needs only a sound solver plus the same blocking clauses — but the *order*, and so which instance or trace you see first, is the backend's own. For a temporal command that also fixes the configuration the whole enumeration is relative to ([LEDGER-014](SEMANTICS_LEDGER.md)). No count taken under `cadical` is ever compared against a jar baseline, and the conformance gauge (`solve-gauge`) deliberately has **no** `--solver` flag at all, so the scorecard cannot accidentally be measured on anything but the yardstick.

### Rung-3 evaluator + self-check net (mt-034) — the "self-verified" promise
The direct three-sorted evaluator (`crates/als-core/src/eval.rs`, translation-ref §6) is an **independent second implementation** of the same semantics the encoder emits as SAT gates; it re-evaluates every found SAT instance against its own goal (`solve_goal`/`enumerate` `debug_assert!`; `als_core::self_check` in checked mode for tests/corpus). Two nets pass clean: the **encoder↔evaluator differential** (brute-force every candidate instance, assert the evaluator's accept count equals the solver's SB-0 count — 15 models spanning quantifiers, closure, subset sigs, field multiplicities, cardinality/int-compare, override, restriction, transpose, comprehension), and the **corpus self-check** (every solved SAT instance across all 167 files self-checks — **0 failures**). Scope-honest notes:
- **The evaluator is a full matched pair over Rung-4 integers (mt-044)** — every arithmetic op, shift (same mask + junk-bit overflow condition), `sum`, and int-ITE the encoder handles, the evaluator evaluates with identical wrap values and the identical per-variable polarity guard, and (mt-051) the pair extends over the one-sided `Int[·]`-cast semantics — cast-emptiness, the set-structure comparison guard, and the constant escape are decided by shared `overflow_guard` predicates (`collect_capable_casts`, `translation_constant`) so the two back ends cannot drift and the differential always compares like for like. The differential fuzz extends over all new ops in both overflow modes.
- **Temporal kinds return a typed error** (never reached: lowering defers temporal before solving).

### Known syntax-level divergences from the reference (tracked, deliberate)
- ~~**`steps`-scope validity checks deferred to resolve.**~~ **CLOSED at mt-067**: both checks the jar makes at command-build time — an increment other than 1 (`for 1:2 steps`) and an open range not starting at 1 (`for 3.. steps`, probe T-08a, rejected with the jar's exact `Unbounded time scope must start at 1.`) — now fire in the resolver, where a `N..`/`N:I` range is first known to target `steps` rather than a legally-growing sig scope. Both are file-level rejects on either side, so the accept/reject answer matches; the increment message is mettle's own (the jar's exact text for that one is not pinned).
- **Identifier Unicode classes approximate Java's** (`char::is_alphabetic`/`is_alphanumeric` vs `isJavaIdentifierStart/Part`); divergence is only possible for exotic non-ASCII identifiers. Now observed once: the mt-013 alloy4fun pass (186k records) found one submission using `€` (EURO SIGN, U+20AC) as an operand where `in` was meant — `Character.isJavaIdentifierPart` classifies currency symbols as identifier characters, `char::is_alphanumeric` does not, so mettle lexes it as a stray character (a precise error) where the jar accepts it lexically and only rejects the resulting expression at type-check. mettle-rejects-earlier is not a wrong verdict on this file (both ultimately reject it), so left as-is; see [docs/reference/alloy4fun-error-pass.md](docs/reference/alloy4fun-error-pass.md) and [docs/reference/alloy6-grammar.md](docs/reference/alloy6-grammar.md) §1.4.
- **Unterminated block comments** are a precise error in mettle; the reference's generated lexer silently ignores a `/*` that never closes. Impossible to hit on well-formed input.
- **Deep expression nesting is a precise `TooDeep` error in mettle, not a crash.** The reference jar suffers a raw `StackOverflowError` on pathological `(`/`{`/binder-chain nesting; mettle's parser now guards recursion depth (`MAX_EXPR_DEPTH = 256`, `crates/als-syntax/src/parser.rs`) and fails with a typed, spanned error instead. A deliberate, better-than-reference divergence (mt-014 Part 1); no real model approaches the limit. See [docs/reference/fuzzing.md](docs/reference/fuzzing.md) §3.

### Resolved this session (mt-014)
- ~~**Binder-as-rightmost-operand (grammar-doc §3.1) over-composes across nested precedence levels.**~~ **Resolved in mt-014.** The jar's actual rule was mapped empirically (≈220 probes against the pinned jar) and implemented as an explicit "binder-composition budget" threaded through both the parser and the printer (`crate::prec::child_binder_budget`, shared so the two can never drift): a binder may be the rightmost operand of exactly one enclosing operator "hop"; a second hop is rejected unless the enclosing operator is a bare `implies` (no `else`) or the `else` branch of `implies … else`, which grant a fresh two-hop budget to their own branch; comparisons and the set-test prefixes (`no some lone one set seq`) never accept a binder operand at all. `q or r and all x: A | body` (the originally-reported shape) is now a precise `BinderNeedsParens` error ("a quantified formula here must be parenthesized"); all previously-accepted single-hop and `implies`-two-hop shapes are unaffected. Full probe table and rule derivation: [docs/reference/fuzzing.md](docs/reference/fuzzing.md) §2.

### Resolved this session (mt-026)
- ~~**A prefix operator wrapping a binder falsely stayed transparent across an already-spent composition hop.**~~ **Resolved in mt-026.** mt-014's rule assumed every ordinary prefix (`!`/`not`, the temporal unaries, `# int sum`, `~ ^ *`) passes its ambient binder-composition budget through unchanged at any budget — never actually verified for a prefix wrapping the binder itself (as opposed to an infix operator's *left* operand). It's wrong: 427 fresh jar probes showed a prefix wrapping a binder is transparent only while the ambient budget is still a fresh `TOP` (chains arbitrarily deep: `always always always all x: A | …` parses); once an ordinary infix operator has already spent its one hop, the prefix does not forward it — `q and always all x: A | …`, `q and not some x: A | …` are syntax errors even though the un-prefixed `q and all x: A | …` is fine. Exactly 6 real alloy4fun codes hit this (`… and always all f: … | …` / `… and not some x: … | …` / `… iff not some x: … | …` shapes). Fixed with one new shared function, `crate::prec::prefix_operand_budget`, used by both the parser (`parse_prefix`, `parse_closure_at_depth`) and the printer (`write_unary`, `write_closure`) — so the two stay in lockstep. Over-acceptance: 320 → **314**. Full probe table and rule derivation: [docs/reference/fuzzing.md](docs/reference/fuzzing.md) §2 ("mt-026" subsection).
